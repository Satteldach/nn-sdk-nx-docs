5.2 Implementing Bans

This section describes the tools and information required for implementing bans, the timing when bans are applied, and their scope.

Tool Required for Implementing Bans (BMAS)

To implement a ban, use the management tool for registering bans, called BMAS (Ban Management System). For more information, see Help in BMAS.
You can use BMAS to register and unregister bans on applications.

You can access BMAS from the following URL. To log in, you need a Nintendo Developer ID.

https://webapp.bmas2.srv.nintendo.net/

Info:

BMAS was renewed on April 9th, 2024, and its URL has changed.


Information Required for Bans

To register a ban in BMAS, you must specify the NSA ID of the user being banned.

When a device app ban is registered, the last login time (which can be checked on BMAS) is used to identify the Switch console that is the target of the ban. For applications that use independent servers, the login ID information can also be used to identify the console. For more information, see 5.3 Selecting the Ban Method.

Identifying the NSA ID

The following methods are available for identifying a user's NSA ID information.

User's Principal ID When Using the NEX Game Server

When an application uses the NEX game server, you can identify the NSA ID of the user based on that user's principal ID information saved on the game server. The principal ID and NSA ID values in NEX have the same value.

Use the NEX Web API or the NEX Management System (NMAS) to view the principal ID information on the game server.

If the application uses the NEX data store or ranking features, you can identify the NSA ID of the target user from the game server if uploaded data or scores for that user exist.

Note that the NEX matchmaking feature can only access the session information on the game server while the matchmaking session is actually being created. There is no way to identify users from previous sessions. Note that identifying an NSA ID later on is not possible during actual operations.

User IDs When Using NPLN

If the application is using NPLN, you can identify the NSA ID from the NPLN user ID. The NPLN user account is a user account created on the NPLN game server (tenant) and is associated with one network service account.
For more information about NPLN user accounts, see NPLN Manual > NPLN Overview > NPLN Architecture.
To identify the NSA ID from the NPLN User ID, you can use either the NPLN Dashboard or the NPLN WebAPI. For more information, see the respective manuals.

  • Identifying the NSA ID from the NPLN User ID in the NPLN Dashboard
    • On the NPLN Dashboard, open, Auth > ID Search and use that page to search for the NSA ID associated with the NPLN user.
    • For more information, see NPLN Manual > NPLN Dashboard Manual > ID Search and Authentication Settings (Auth).
  • Identifying the NSA ID from the NPLN User ID in the NPLN WebAPI
    • You can use a feature similar to the NPLN Dashboard ID search feature from the WebAPI.
    • For more information, see NPLN Manual > WebAPI Usage Manual.
NSA ID Tokens When Using Independent Servers

If the application uses an independent server, the NSA ID can be identified from the user's NSA ID token that is sent to the independent server.
The independent server can view the NSA ID and login ID information from the internal information in the decrypted NSA ID token.
For more information, see the Nintendo Switch Independent Server Setup Manual.

Customer Support Number Viewable From the User Page

The number for customer support displayed on the User Page in the Switch HOME Menu can be used to identify the NSA ID of the applicable user account.
The method of determining the NSA ID by directly contacting the user is expected to be used when lifting bans rather than when applying them.
For more information about converting the support number to an NSA ID, see Nintendo Switch Independent Server Setup Manual > Independent Server Operation.

Info:

The ID conversion tool that was provided in the previous version of BMAS is no longer provided in the renewed version of BMAS.

Identifying and Narrowing Down the Login ID

When you register a device app ban, you must specify both an NSA ID and a login ID to apply the ban to a specific Switch console.

Use the search tool in BMAS to get the list of login IDs associated with a particular NSA ID.

Each login ID in the obtained list represents a Switch console that has been linked at some time to the Nintendo Account associated with the NSA ID. Note that this list includes the login IDs for Switch consoles that are no longer linked to the Nintendo Account.

You are banning a user for their behavior, so you do not want to target a Switch console that this person is no longer using. To avoid this, use either of the following procedures to identity or narrow down the login ID that is the target of the ban.

Specifying the Login ID

There is currently no method available for identifying a specific Switch console from the login ID.
However, if the application is using an independent server, you can get the login ID from the NSA ID token sent by the independent server. By controlling the independent server, you can identify combinations of NSA ID and login ID that represent specific Switch consoles.
If the application is using NEX or NPLN and is not using an independent server, you cannot use the NEX and NPLN mechanisms to reference the login ID information included within the NSA ID token.

Narrowing Down the Login ID

When you get the list of login IDs on BMAS, the list screen shows the last login time for each combination of NSA ID and login ID.
You can use this information about the last login times to determine which Switch consoles were recently used by the user you want to ban.
If several login IDs are associated with the NSA ID, narrow down the Switch consoles as much as possible before implementing the ban.

Timing for Applying Bans

The measures for blocking access to the service are implemented on the authentication server from the point when the ban is registered in BMAS.
However, authentication information is cached on the Switch console, so there might be a delay of up to one day from the time when the ban is implemented to when the user is actually prevented from using network services.

Info:

If the application uses the NEX game server, using the NMAS forced disconnect is effective at the following two timings.

  • Immediately after applying a ban
  • One day after applying a ban (after authentication information cached on the Switch console has expired)

This is because even after applying a ban, credentials are not checked until the user attempts to log in to the NEX game server again.

Lifting Bans

If you want to lift a ban for some reason, you can do it using BMAS. As with applying a ban, lifting a ban also requires the NSA ID and login ID for specifying the target.

Policy for Implementing Bans

Bans applied in BMAS only affect operations within specified applications.
Publishers can implement bans using BMAS at their discretion. It is the publisher's responsibility to consult with a legal advisor when appropriate.

  • If you have made adjustments with the legal department in advance and set an application-specific ban policy, follow that policy.
  • If there is no application-specific ban policy, consult with the legal department as required before adding any bans.

The following are examples of where bans might be appropriate.

  • When activities that interfere with running the game occur
  • When illegal content is posted or shared
Note:

For example, if the Japanese and non-Japanese publishers are different, bans applied by the non-Japanese publisher might be lifted by the Japanese publisher. Consider measures such as verifying the policies for each publisher before implementing the ban.

Managing Ban Targets

Publishers are responsible for determining when to implement bans, including ensuring that they have the legal right to ban user(s). Publishers must also handle user inquiries about bans.
Consider measures such as managing the ban information, so that the ban target and reasons for banning can be referenced later if banned users were to contact the publisher.
Note that lifting bans upon user request is not mandatory, but implement bans appropriately with the expectation that users may contact you about them.
