5.4 Authentication and Authorization Sequence

This section describes the standard linking sequence.

Link Sequence

The procedure for linking accounts for China to Switch applications and the independent servers is mediated by nn:account.

Application
Number Description
1 The user begins the process of linking an account for China by performing an operation in the Switch application.
2-4

If the application is not connected to the independent server at this time, the procedure described in 3 Connecting to an Independent Server is performed.

The independent server generates a state value and a nonce value and saves and associates them with the session.
The state value is meant to prevent CSRF attacks. The value is used to confirm that the application that started the authorization procedure is the same as the application in step 9 with the result of the authorization procedure.
The nonce value is meant to prevent replay attacks. Both strings are difficult to guess.

5

The following parameters, which include the values for state and nonce generated in an earlier step, are used to make an authorization request for nn:account.

Item Description
scope The scope of the requested permissions.
state The value generated in step 3.
nonce The value generated in step 3.

code id_token is automatically specified for response_type.
The client ID and the redirect URI linked to the Switch application are automatically specified for client_id and redirect_uri.
6-8

The authorization procedure starts if the login status of the account for China is abnormal, or if the user has not approved the application making the request.
The following response is ultimately returned for the application.

Item Description
code The authorization code. Required before you can get the token.
id_token Required before you can get the token.
state Returns the state value just like it was specified in the authorization request.
9

The Switch application sends the obtained response request to the independent server. You can send this data by any method, but make sure that you encrypt the communication channel.

10

Verification of the ID token and authentication of the user. For more information about the verification method, see the 5.7 ID Tokens page.
If the only objective is to authenticate the user and the account API is not being used, the procedures in steps 11 through 14 are not necessary.

11

The authorization code sent from the application is verified using the value of c_hash in the ID token.
For more information about the verification method, see Verifying the Authorization Code Using the c_hash Value on the 5.7 ID Tokens page.

12-13

Performs a token request using the authorization code.
Specifies the following parameters and casts the token request to the accounts for China server.
For more information, see the section in this document about the specifications for token requests.

Item Description
Authorization Basic authentication based on the client ID and the client secret.
code The authorization code obtained as the result of the authorization request.
client_id

The client ID, issued in advance.
redirect_uri

Fixed to nintendo://${application ID}.app.
All letters in the application ID must be lowercase.
(Example: nintendo://0123456789abcdef.app)
grant_type Fixed to authorization_code.

If the token request is successful, the following tokens can be obtained.

Item Description
access_token A token required to use the Account API.
token_type The type of token. Fixed to Bearer.
id_token

Included if scope=openid was specified.

refresh_token

Included if scope=offline was specified.
A token for reacquiring the access token.
expires_in The access_token expiration date.
scope

Stores an array of user-authorized scope values from among the values specified in the authorization request.
14-16

The application is linked to the internal ID of the account for China, if necessary, and then the access token and request token are saved.
101

The access token can be used to run the account API. For more information, see the 5.8 Account API section of this document.

201

If the access token has expired, it can be reacquired using the refresh token. For more information, see the 5.6 Token Requests section of this document.

Notes When Linking

The internal IDs for accounts for China are always unique within a single server environment. However, uniqueness is not ensured across multiple server environments.
Because the independent server connects with Nintendo servers in multiple environments, identify the account for China using the combination of the iss value in the ID token (or its FQDN) and the internal ID.
If your independent server is linked to both network service accounts and accounts for China, also note that these links might be severed or changed via operations conducted by Nintendo.
Do not act on your own accord with the independent server to convert the internal ID of an account for China to the internal ID of a network service account, or vice versa.

When the Requested Scope Is Not Authorized

For a scope that does not require authorization, the processing might advance without user authorization. In such cases, use a sequence that does not confuse the user. For example, avoid the repeated display of authorization without any explanation to the user. We recommend advancing the process using only the information that can be obtained with the authorized scope.

Any scope data authorized by a user can be acquired as a response during token requests.
