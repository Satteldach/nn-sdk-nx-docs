4.7.3 ID Tokens

The specification for Nintendo Account ID tokens is nearly identical to that for 3.5 NSA ID Token Specifications.

Note

It is prohibited to decode a Nintendo Account ID token within a Switch application and then use that information.

ID Token Format

Header

A JSON object containing the following properties.

Key String
Type
Description
alg string

The signature algorithm. Fixed to RS256.
kid string

The identifier for the public key used in the signature.

jku string(url)

The endpoint serving the public key.

Claims

A JSON object containing the following properties. Additional properties may be added in the future without notice.

Key String
Type
Description
iss string

The base URL of the Nintendo authentication server that issues the token.
sub string

Represents the Nintendo Account identifier.

Note

There are two types of Nintendo Account identifiers, as listed below. The identifier that can be obtained will differ, depending on when the link with the Nintendo Account started. For more information, see 4.6 Migration From NAID to PPID.

  • NAID: An ID that is unique across all clients. (A 16-digit alphanumeric with lowercase letters.)
  • PPID: An ID that is different for every client. (A 28-digit alphanumeric with uppercase letters.)
aud string

The client ID specified in the authorization request.

iat number

The time when the token was issued. The format is a UNIX timestamp.
exp number

The period during which the token is valid. The format is a UNIX timestamp.

jti string

The identifier issued for individual tokens. The format is UUID v4.

typ string

The type of token. Fixed to id_token.

ac:sid string

If the Nintendo Account identifier is PPID, the client ID is included.
The existence of the ac:sid element provides a way to determine whether the sub value is an NAID or a PPID. For more information, see 4.6 Migration From NAID to PPID.
c_hash string

The hash value for verifying the authorization code.
Included when response_type=code id_token.

at_hash string

The hash value for verifying the access token
Included when response_type=token id_token.

nonce

 string The nonce value that was set during the authorization request.
country string

The user's country of residence. The format is ISO 3166-1 alpha-2.
This property is only included if the user.basic or user.country scope is authorized by the user.
The countries where a Nintendo Account can be registered may increase in the future as the service expands. Implement your independent server to operate without problems even if more countries can be set for this property in the future.

ID Token Verification Procedure

With the exception of steps 7 and 8, the procedure for verifying an ID token is the same as the verification procedure described in 3.5 NSA ID Token Specifications.

Number Verification Content Notes
1

Verify that the token is in JWT format.

 Before proceeding to other verification processes, the first step is to verify that the ID token is in the correct format.
2

Verify that the value of alg in Header is RS256.

 This verification step is necessary to reject invalid ID tokens, such as those with an alg value of none.
3

Verify the signature attached to the ID token.
Use the Get member function to access the URL stored in jku for Header to get the public key or certificate to verify the signature.
The data that can be obtained is called a JSON web key set (JWKs) and is expressed as a JSON object array containing public keys and certificates.
The JWKs contains the kid property to specify which key to use.
The key information matching kid in Header of the ID token is obtained from the JWKs to verify the ID token.

The signature verification algorithm is fixed to RS256 (RSA-SHA256) as shown in the alg value for Header.
Use the x5c value (certificate in X.509 format) contained in the JWK or the public key's n value (Modulus)/e value (Exponent) for verification.

Signature key rotation is every 24 hours.

To keep up with changes to the signature key, the independent server must access the URL indicated by the value of jku and get the JWKs using one (or both) of the following methods.

Getting the JWKs On Demand

In this method, server-to-server communication is conducted to get the JWKs if there are no cached JWKs when an ID token must be verified.

  1. Check whether a JWKs is cached that corresponds to the kid value in Header.

    If it is not, execute the following procedure.

  2. Verify that the URL of the jku value in Header matches the URL provided by the Nintendo authentication server.

  3. Use the Get member function to request and get the JWKs for the URL of the jku value.

  4. Cache the obtained JWKs.

Getting the JWKs Using a Periodic Batch Job

This method gets JWKs periodically using a separate process from the one for verifying the NSA ID token.
The rotation interval during normal operations is 24 hours, but in the case of unforeseen circumstances like the leaking of keys, the keys might be replaced before 24 hours pass. For this reason, run the process at five-minute intervals.

The JWKs contains three generations of JWK data to prevent situations where a JWK corresponding to a signature cannot be obtained, even when the ID token is cached in an intermediate system.
4

Verify that the value of iss in the Claims matches the Base URL on the Nintendo authentication server.

 The Base URL of the Nintendo authentication server must be preregistered in the independent server in advance.
5

Verify that the value of iat in Claims is in the past.

A calculation error of around 10 seconds can be tolerated to allow for time differences among systems.
6

Verify that the value of exp in Claims is after the current time.

 A calculation error of around 10 seconds can be tolerated to allow for time differences among systems.
7

Verify that the aud value in Claims matches the local client ID.

 This verification is necessary to prevent connections from other companies' applications.
8

If nonce was specified in the authorization request, this process verifies that the nonce value in Claims matches the locally issued nonce value.

 Verification of nonce is designed to prevent replay attacks by duplicate of authorization responses.
JSON Web Key Set (JWKs)
Key String
Type
Description
keys array

An array that includes the following JSON objects.


Key String Type Description
kid string

Indicate the identifier for the key used in the signature.
e string The exponent value of the Base64-encoded RSA public key.
n string The modulus value of the Base64-encoded RSA public key.
x5c array The Base64-encoded certificate chain in X.509 format.
alg string The signature algorithm. Fixed to RSA256.
kty string The key type. Fixed to RSA.
use string

The use of the key. Fixed to sig.


Verifying the Authorization Code Using the c_hash Value

If response_type=id_token code was specified in the authorization request, the ID token will include the c_hash value, which is a hash value for the authorization code.
By using this hash value to verify the authorization code, you can confirm that the authorization code has not been altered in the application or somewhere en route.
Use the following verification procedure.

  1. Use the SHA-256 algorithm to hash the code value included in the authorization response.
  2. Encode the 128 bits of the first half of this hash value using base64url encoding.
  3. Compare this value with the c_hash value in id_token and confirm that they match.


Verifying the Access Token Using the at_hash Value

If response_type=id_token token was specified in the authorization request, the ID token will include at_hash, which is a hash value for the access token.
By using this hash value to verify the access token, you can confirm that the access token has not been altered in the application or somewhere en route.
Use the following verification procedure.

  1. Use the SHA-256 algorithm to hash the access_token value included in the authorization response.
  2. Encode the 128 bits of the first half of this hash value using base64url encoding.
  3. Compare this value with the at_hash value in id_token and confirm that they match.
