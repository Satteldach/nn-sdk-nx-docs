To implement scenes in the application where user accounts are selected, the application must take steps to get user account information and to change the states of the accounts. The application can use the following features for that purpose.

Get user nicknames

Change the signed-in and signed-out states of user accounts.

Implementing Scenes For Selecting User Accounts

The policy with the Switch is to guide players naturally to the proper use of user accounts by coinciding the selection of user accounts with operations like the selection of save data or the selection of game characters. If at all possible, implement your application so user accounts are selected in a way that is consistent with user operations. Avoid implementations where the application automatically selects which user account to sign in without any selections being made by the user.

You can choose among several ways to implement scenes for selecting user accounts, as follows.

Implementation Description
The application uses the account management applet. The account management applet has a UI that prompts players to select or switch users. Based on the internal user account ID returned from this applet, the application uses the account library to sign in and sign out user accounts.
Create an application-specific UI. Use the account library to list the user accounts registered on the console, and implement an application-specific UI to select or switch users and sign in or sign out.
Select the user in the system itself before the application starts.

Have the system call the account management applet and start the application with one user account already selected. An explicit sign-in process on the application side is required for the selected account.

Changing the Signed-In and Signed-Out States of User Accounts

In scenes in the application that involve the selection of user accounts, perform the appropriate sign-in and sign-out processes if users are being added or trading turns. The Switch system features operate on the assumption that the user account being used by the game is in the signed-in state. For this reason, unexpected outcomes could occur if the user accounts selected in the application differ from the signed-in states of accounts in the system. Similarly, have the application perform the user account sign-out process when the application transitions to scenes where a user account is not used.

For more information about the differences between when the user account is signed in and when it is signed out, see 3.3 User Account States. For more information about user account sign-in and sign-out processes, see 5.2 Different Designs for Supporting the Switch Account System.

The following table presents specific examples of scenes where accounts are signed in and signed out.

Scene Where Processing Takes Place Process
More users playing together. One example is transitioning to two-person play mode. Sign in other user accounts in addition to those already signed in.
A switch in players. Sign out the user account that is currently signed in, and then sign in a different user account.
Users stop playing. (Example: Return to the title screen.) Sign out the user accounts that are currently signed in.

Sign-in and sign-out processes are generally completed instantly. However, if the application is using the network features, accessing a network service account after signing in may take some time.

Info

There is no need for users to be signed in and out every time if the game requires multiple users to frequently join and leave. Implement a measure to sign out user accounts after a long time has passed without them being used for gameplay. For example, assume that four users are playing a turn-based board game. Rather than having each user sign in and out on each turn, it would be better to have all four players remain signed in for the duration of the game.

Support When Sign-In Processing Cannot Be Performed

On Switch consoles with system version 6.0.0 and later, the user account states include one state where the user account cannot sign in. In cases where an application requests that users select a user account for sign-in purposes, ensure that user accounts in this state cannot be selected. In cases requesting that users make a selection for purposes other than signing in, this state does not need to be considered.

When using the account management applet, the option to specify whether user accounts in this state are selectable can be set when the applet is displayed. For more information, see 5.1.3 Feature Group 3: Account Management Applet.

Supplementary Features for User Account Selection

You can use the following options to improve usability and to decrease costs associated with the application.

Get the last user account signed in to the system

A feature is provided for getting the last user account that was signed in on the console. (The value that can be obtained is reset when the Switch is turned off.) If you are implementing a custom UI for game scenes where a user account is selected, players may find it more convenient if you preferentially display this user account when the application starts (for example by controlling the focus of the cursor). Support for this functionality is not required. The selection UI displayed by the account management applet (described in the next section) initially places the cursor focus based on this information.

Option to Select User Before Application Starts

The Switch has an option for using a system feature to select the user before the application starts. The use of this feature is configured as metadata in the application. If this option has been enabled, when the application is selected in the HOME Menu, the account manager applet is displayed to request the selection of a user. For an application that is deployed on multiple platforms, you can use this option to implement a version for the Switch without making any major changes to how accounts are handled.

Workaround for Cases Where There Are Redundant Requests to Select a User

On consoles with system version 6.0.0 and later, the situation with licenses in the application might force a user to be selected before the application can start, regardless of how the option for selecting a user has been set. For applications designed to select a user after startup, this can result in situations where the request to select a user is made redundantly, first by the system and then by the application. An option was implemented in SDK 7.0.0 and later versions to avoid this redundancy. The option enables the application to use the user account information from the system's user-selection process if that process was performed prior to application startup due to the license situation. This option is configured as application metadata. When this option is enabled, the application can determine whether the user-selection process was performed in the HOME Menu and, if so, get the information about that selected user. This provides a way to omit a redundant user-selection process inside the application when it has already been performed in the HOME Menu.
