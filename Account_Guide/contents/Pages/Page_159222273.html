5.2.2 Design 2: Select One Account When Selecting Save Data

This example implements a proprietary UI for an application where each user has several save data slots. You can set the user account at the same time as save data selection. With the Switch system, the size of the account save data region is set in advance, so the assumption is that the specification calls for each user to have a maximum of N slots of save data.

Advantages
  • Selection of the user account is completed at the same time as save data selection.
    • Effort within the user experience can be reduced, promoting using separate save data for each player.
Important Information
  • Generally speaking, you must implement the UI for your application.
    • The feature provided by the account management applet is the selection of a user account from among the accounts registered on the system, regardless of sign-in status. As a result, the application must support checking whether the number of save instances data that can be created is within the maximum and sending notifications when users who have reached the maximum number of save data instances that can be created are selected. Also note that if you are using the "user that cannot be selected" feature in the user selection UI of the account management applet, the applet side cannot display the reason that the user cannot be selected.
    • When implementing a proprietary UI, you must provide support for users who cannot sign in. For more information, see 5.1.1 Feature Group 1: Displaying User Accounts and Changing Their States.
  • For applications that include specifications for multiple users playing simultaneously, there is no way to specify users other than the first. For this reason, additional users are treated as guests.
    • This design is suitable if users after the first user only perform light support operations and the additional users are clearly identified as guests. (Their save data is not retained.)
    • You can also add a sequence to the application to allow users to select user accounts for the other users separately at the beginning of scenes where more than one person is playing. (Also see Design 3-3.)

Info

In version 6.0.0 and later of the NX system, a forced user selection can occur before starting an application, in conjunction with the application's license. However, in some cases user selection is duplicated for applications that have implemented this pattern in the HOME Menu and in the application.

As an option for avoiding this situation, a setting in SDK version 7.0.0 and later allows using selected user account data when the system has already performed user selection for reasons related to license. When this option is enabled, the application can get data about whether user selection occurred from the HOME Menu and data about the selected user. Using this data, you can achieve implementations that skip repeating user selection in the application when users were already selected in the HOME Menu.
