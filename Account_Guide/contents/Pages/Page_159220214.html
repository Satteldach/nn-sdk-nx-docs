5.1 Premises When Considering Your Specifications

When discussing the specifications for your application, consider the following.

  • Assume that there will be one user for each user account.
  • Assume that users operating the Switch are logged in, and that logged-out users are not operating the Switch.

Also note that the application can use the following features.

  • Feature Group 1: Display of User Accounts and Changes to Status
  • Feature Group 2: Associations With Network Service Accounts
  • Feature Group 3: Account Management Applet

For more information about implementing these features, see documentation such as the API Reference, which is included in the SDK's account library.
Some of the descriptions may be for features that are not yet available. For more information, see the specific documentation for each feature.

Assume that there will be one user for each user account.

Design your application with the assumption that each user (defined as a real-world Switch user) uses one user account. Services to be offered in the system, such as a feature for transferring save data between systems, will support operations at the user account level. If your application guides multiple users to use multiple save slots in a single account save data region, these services may not operate as intended for users.

Assume that users operating the Switch are logged in, and that logged-out users are not operating the Switch.

As noted in 3.3 User Account States, ensure that users operating the game are logged in.

Conversely, if a user account is in the logged-out state, assume that the user associated with that account is not operating the Switch system. If the save data of user accounts is accessed while the accounts are in the logged-out state, depending on what happens, it might provide an impression to users that their save data has been altered without permission. If your application will change the save data of user accounts in the logged-out state, consider adopting a style like the following.

  • Stage or design a way of letting users understand that their own data can be altered even while they are not operating the system.
    • Express naturally occurring changes within the application, such as weather and disasters, or changes brought on by the actions, including attacks, of other users.
    • Design games where multiple users collectively advance the game.
  • Stage an event such as delivering a package or letter, which the user receives the next time they log in.
