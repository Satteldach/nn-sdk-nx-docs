This section describes the NMETA file required to build a ROM, as well as the processes of building and testing ROMs and saving the build environments.

ROMs can be created by specifying an NMETA file when building a Visual Studio Project that was created according to the instructions in 4.2 Creating Visual Studio Projects.

Info:

You can also build ROMs without using Visual Studio. For more information, see NintendoSDK Documents > Features > Building > Build Systems > Guide to Setting Up the Environment.

NMETA Files

NMETA files define the associated data for an application or downloadable content. The NMETA file specifies application-related information such as the application ID, the release version, and software legal information, as well as data like the title name that are referenced by the HOME Menu and other system features.

Info:

You create legal information using SLIM. For more information about the creation process, see System Features Guide > System Menus > HOME Menu > Options.

Creating and Editing NMETA Files

For more information about the NMETA file settings and how to create NMETA files, see NintendoSDK Documents > Features > Building > Creating Application Images > Writing NMETA Files, in addition to Tutorial > Application Development > Preparing the NMETA File.

NMETA files can also be edited using AuthoringEditor. AuthoringEditor can be used to edit NSP files after they have been built and to call NSP files directly from within Visual Studio. For more information about using AuthoringEditor, see NintendoSDK Documents > Features > Building > Creating Application Images > Tool Reference > AuthoringEditor.

Building Application ROMs

The products that can be submitted to Lotcheck from the Releases tab of the dashboard are referred to as applications. In addition to full retail applications, this term also refers to demo applications and multi-application cards.

Note:

To create the first patch, you need the NSP file of the initial version of the application, and it must have passed Lotcheck. To create the second and later patches, you need that NSP file and also the NSP file of the previous patch. Be sure to save and not delete these files.

Info:

To use crash reports, you need the NSS file that is created at the same time as the NSP file. Be sure to save and not delete this NSS file, not only for the initial application, but also for patches.
For more information about using crash reports, see 7 Support After Release.

Initial Release

The initial release of an application refers to the first version of a full retail application, demo application, or multi-application card application that was created and submitted. On Nintendo Developer Portal, the initial release is the one that is created under Releases with a release version of 00.

Build Procedures

  1. Configure the following options for the Visual Studio project properties.
    1. Set the Application Program Format property to NSP.
    2. Enable Dead-stripping.
  2. Specify the NMETA file in the project file.
  3. When creating a master ROM, set the solution configuration to Releases and then build the application using Visual Studio.

For the detailed build procedures, see NintendoSDK Documents > Tutorial > Application Development.

Demo Applications

The build procedure for demo applications is the same as the build procedure for full retail applications except that when creating the ROM for a demo application, the Basic > Demo check box must be selected in AuthoringEditor.


Patches

Patches consist of data for updating full retail applications and demo applications. On the Nintendo Developer Portal, products created in Releases with a release version of 01 or later are patches.

Info:

When compacting an application, see Nintendo Switch Patch Guide > Switch Patch Features > Application Compaction.

Building Patches

Read the Patch Guide documentation before you begin creating a patch.

  • For the AuthoringTool patch build procedure, see
    NintendoSDK Documents > Features > Patches > Building and Running a Patch.
  • For the VSI patch build procedure, see
    NintendoSDK Documents > Features > Building > VSI > Creating Patches.

Multi-Application Cards

For more information about build procedures, see NintendoSDK Documents > Features > NX Development Cards > Multi-Application Cards.

Building ROMs for Downloadable Content

Products that can be submitted to Lotcheck from the Downloadable Content tab of the dashboard are referred to as downloadable content, or DLC. Downloadable content cannot be updated using application patches. To update an existing DLC product, you must create and submit an updated version of the DLC itself rather than using an application patch.

When you submit the master ROM, you must collect together all of the data for the DLC and submit it as a single package. This package is in a format for master ROM submission, but it is not treated as the data for a single piece of downloadable content.

Build Procedures

For more information about building downloadable content, see NintendoSDK Documents > Features > System > aoc Library > Creating Downloadable Content.

Testing

Final testing for applications submitted to Nintendo Lotcheck must be performed in an environment that meets certain conditions, regardless of the application sales format. For more information about these conditions, see NintendoSDK Documents > Testing Applications.

The SDEV can be used to test the release version of the NSP file. However, you must also test using the EDEV. In addition, when selling card-based software, also test for writing the application to an NX development card and starting from the NX development card.

Installing Applications

When testing, the way you install an application will differ, depending on the application type.

  • When testing after writing to an NX development card:
    See NintendoSDK Documents > Tutorial > Writing to NX Development Cards.
  • When testing after installing to system memory:
    See NintendoSDK Documents > Tutorial > Installing Applications on Development Hardware.

Installing Downloadable Content

To test downloadable content, put the NSP file for the DLC on an SD card and then use DevMenuCommand to install the content. For more information, see NintendoSDK Documents > Features > System > aoc Library > Managing Downloadable Content.

Saving the Build Environment

Export and save any used build environments because they can be used when developing patches. For more information, see Nintendo Dev Interface > gear icon on the upper right > Documentation > NDI_Manual-en > 4. Using NDI > 4.10 Exporting a Development Environment (MegaZarf Format).
