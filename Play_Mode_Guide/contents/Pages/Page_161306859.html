5.2 Approaches for Supporting the Basic Policies

This section describes approaches for supporting the following basic policies, in addition to describing when and how to decide not to support them.

Policy 1 The application as a whole supports play in TV mode, tabletop mode, and handheld mode.
Policy 2 Users can switch between modes at any time while the application is running.

Support for Policy 1

There is a difference in performance for the Switch when the system is placed in the Switch dock with the application projected on the TV screen, and when the system is removed from the Switch dock.

In addition, the touch panel cannot be used unless the game screen is displayed on the console screen.

With the Switch, various scenarios are either possible or impossible, depending on the play mode.

When you stop using features that differ from mode to mode and use only features that are supported in all modes, you can easily offer support without making the user strongly aware of the basic policies.

Alternatively, we also want to avoid lowering the value of the application and the Switch platform as a whole, by avoiding functionality that will require adjustments.

We recommend the following when prioritizing your planning approaches.

  1. Consider application specifications that can be fully realized on the Switch without getting caught up in the restrictions that are in place for the basic policies.
  2. If those specifications include ways of playing that are impossible in some play modes, consider replacement specifications that would enable users to recognize that they are still playing the same game.
  3. If it proves impossible to offer the same experience in every mode, consider releasing a Policy 1 exception title.
Note

We have few cases, and there is no standard as to which cases are considered not to support policy 1.

For this reason, if all or part of the application cannot be played in a particular mode, we may ask you to explain the reason for your decision.

If as a result of considering the "alternative specification" the game experience changes, as in step 2, and you are contemplating whether it would be more appropriate to disallow play in that mode, consult Nintendo.

In the future, we plan to post cases that show reasons for deciding not to support the basic policy in our 7 Supported Examples. For now, we are considering the following as possible reasons:

  • Applications for sports games where the Joy-Con is detached and swung around.
    • Alternative operations using command inputs were considered, but the experience was diminished when compared to swinging the Joy-Con.
    • The game will be promoted as a game in which players swing the Joy-Con around.
    • Due to the concept of the application, it should be obvious to the user that the game cannot be played with the Joy-Con attached to the console. For this reason, the application will not support handheld mode.
  • Application for drawing pictures using the touch panel.
    • Alternative operations using the analog stick and commands were considered, but it was different from the technique of drawing pictures.
    • Due to the concept of the application, the touch panel is indispensable. It should be obvious to the user that the game cannot be played in TV mode. For this reason, the application will not support TV mode.
  • Application for a party game in which two or more players hold one Joy-Con each to play.
    • It is not possible to operate with the Joy-Con attached to the console.
    • Due to the concept of the application, each player must hold a Joy-Con, and it should be obvious to the user that the game cannot be played in handheld mode. For this reason, the application will not support handheld mode.

The preceding reasons are merely examples and there may be other reasons. However, the fact that the nature of the application makes it obvious to the user that the game cannot be played in a particular mode is an important point when determining whether the application supports the basic policy.

Support for Policy 2

If the application supports Policy 1, it can probably support Policy 2, which is the ability to switch between TV mode, tabletop mode, and handheld mode at any time while the application is running.

Even if some scenes in the application do not support all play modes, consider implementing the following measures to minimize user discomfort when switching between modes.

  • Display a message indicating that the player will be returned to a scene where switching is possible (a scene that supports all play modes), and then return the play to a scene that is convenient for the application.
    • For example, consider an application that allows 4-person play with 4-way split screens only in TV mode. If the system is removed from the Switch dock during 4-person play, a message is displayed that states: "4-person play is a game mode exclusive to TV mode. You will be returned to the player number selection screen." The player will then be returned to the player number selection screen.
  • After displaying a message indicating the need to return to the original play mode, wait until that return occurs.
    • Another case is where various scenes within the game require touch panels and it is difficult to interrupt the scene. If the player switches to TV mode during such a scene, a message is displayed that states: "This game mode is exclusive to tabletop mode and handheld mode. To play on the TV, please finish this game mode first, and then place the system in the Switch dock." The application will then wait for the system to be detached from the Switch dock.

For more information about alternative approaches for features that are not available in every play mode, see 6.2 Using Features That Vary by Play Mode.

For information about user-facing terms, see Nintendo Switch Terminology.

Depending on the type of application, however, when a user cannot perform operations while attaching the Joy-Con to the console or the classic-grip accessory, creating a pause in the application may make it user-friendly.
