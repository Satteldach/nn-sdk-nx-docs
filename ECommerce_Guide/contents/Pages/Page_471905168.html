7.4.3.1 Overview

Overview

The following types of Nintendo eShop server APIs are used for subscription service items.

  • APIs that are only available for use from an independent server, such as those for referencing available license information, and those for activating subscription service item licenses
  • Debugging APIs that are also available from a PC or other device, such as for setting and clearing errors

Add the path described in the reference to the fully qualified domain name (FQDN) of the subscription service item API endpoint, and send an HTTP request.

API Endpoint FQDN

The FQDN of the API endpoint depends on the environment. For more information, see 9.1 Using Independent Servers > Correspondence Between Environment Identifiers and FQDNs of Subscription Service Item API Endpoints.

Authentication

To use the various APIs, you must use Basic Authentication with a client ID and secret. For more information about issuing a client ID and secret, see 4.1 Usage Request on OMAS.
Before using the server API, you must add trust for the private Nintendo CA. For more information, see 9.1 Using Independent Servers.

Limitations on the Volume of API Requests

Although there is currently no explicit limit on the volume of calls you can make, avoid implementations such as the following that would lead to high load on the Nintendo eShop server.

  • A system where many consoles access the Nintendo eShop server simultaneously after maintenance, such as when checking for licenses immediately after the application starts
  • High frequency API calls, such as when the application periodically gets license information after startup

We recommend that you either only get license information when the user uses an item or service (that is, when it is necessary to check for a license), or use purchase notifications. For more information about purchase notifications, see 2.4 Service Item Purchase Notification Feature.

Note

If the Nintendo eShop server is subjected to a high load, it may not be able to provide stable service.

Character Encoding

Responses are created using UTF-8 as the character encoding.

start_datetime

start_datetime, found in both the API for referencing license information and the API for starting license information, represents the date and time that the current subscription period was activated. This start_datetime value does not change, even if the validity period has been extended by the purchase of subscription service items that include auto-renewal. If a validity period ends and then a new validity period begins, this value represents the date and time of the start of that latter validity period.

Example 1:

A 30-day subscription service item is purchased and begins being used on April 1, 2020. An additional 30-day subscription service item is purchased on May 1 before the validity period expires. When it is May 20, the value of start_datetime is 2020/4/1.

Example 2:

A 30-day subscription service item is purchased and begins being used on April 1, 2020. The validity period expires on May 1, and later, on May 15, an additional 30-day subscription service item is purchased. When it is May 20, the value of start_datetime is 2020/5/15.

Handling Errors

Use the HTTP status code of the response to determine whether the subscription service item's function passed or failed. If a HTTP status code other than 2xx is returned, the request failed.
When an error occurs, the error description will generally be in the following format.

{"error":{"code":"1201","message":"api not found"}}

However, some errors are returned with different response bodies (such as blank). For this reason, make sure that no issues (such as stopping) occur.

For more information about handling and displaying errors in Switch clients, see 7.4 For Developers.
