4.6 Guidelines

The guidelines for implementing NEX are designed mainly to prevent the quality of service from suffering due to excessive load on the game server.

This section describes the guidelines that require particular attention and introduces recommended methods of implementation.

For more information, see the Nintendo Switch Guidelines.

Restrictions on Frequency of Calls to NEX API

NEX functions that trigger server access can increase the server load if they are called too often, so a restriction has been set on call frequency to prevent this problem from happening.
The following examples show some situations where it is easy to call functions too many times.

Ranking

The restriction on the frequency of calls to the RankingClient class is stricter than the restrictions on other server service features, so you must be careful starting from the planning stage.

If you plan to use a lot of categories and move the ranking board while scrolling, chances are high you will call RankingClient too many times. In that case, we recommend using Ranking2Client instead.

If you are using RankingClient, we recommend getting the ranking data one time after logging in to the game server and then only when the player's own score is updated, and otherwise calling the RankingClient::GetCachedTopXRanking() function to use the cached data.

Data Store

If you plan to display lists of data in the application for data searches and the like, we recommend using the metadata for the data shown in the lists.

The DataStoreClient::GetObject() function, which downloads data that has been uploaded to the storage server, can only download one set of data at a time. If you use this function to get data to display in a list, chances are high you will call the function too often.

The DataStoreClient::GetMeta() function, which gets metadata, can retrieve up to 100 sets of metadata at a time.
One set of metadata has a maximum size of 1024 bytes. If you plan to use metadata to display lists of data, make sure the data can fit within this range.

Prohibition of Implementing Independent Auto-Matchmaking

Use MatchmakeExtensionClient::Automatchmake() when implementing automatic matchmaking specifications in the application.

When the processes of creating, finding, and joining matchmaking sessions are controlled in the application and auto-matchmaking is implemented independently, you might face situations in the production environment where errors occur and matches cannot be made if you have not performed sufficient testing. To realize this kind of auto-matchmaking, you must use a sufficient number of test clients and test the process under a variety of conditions. It is usually difficult to perform adequate testing ahead of time, so the guidelines prohibit implementing your own auto-matchmaking process.

Auto-matchmaking using the MatchmakeExtensionClient::Automatchmake() function has been adequately tested and is designed so problems are unlikely to occur in the production environment.

The following kinds of problems can arise when you implement your own auto-matchmaking process.

  • Search results become fixed due to inadequate search criteria, creating sessions where the search targets are not included and matches are not established.
  • If multiple users try to automatically join the same session at the same time, some of the join-in processes might fail and create errors that users cannot handle.
  • If new sessions are not created when candidate sessions are not found as a result of the search, the number of joinable sessions may decrease and lower the overall matchmaking success rate.
