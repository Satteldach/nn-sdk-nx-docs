5.2 Data Stores

Using Both a Storage Server and the Game Server

When using the data store feature to save data, that data can be saved on a storage server or on the game server.

The following table shows some of the advantages and disadvantages of each method.
Storage Server
Game Server
Maximum size for a single piece of data 10 MB 1024 bytes
Number of pieces of data that can be processed at one time 1 100
Specifying a data ID when uploading data No Yes
Processing speed Slower than when using the game server. -

However, by using both a storage server and the game server in combination, you can take full advantage of each. For example, if you store the replay data on the storage server and the thumbnails for that data on the game server, you can first get all of the thumbnails and then get only the needed replay data from the storage server.

Using Data Stores as a Counter

Data stores can be used to store data that functions as a counter for actions taken by game players or ratings submitted by game players.

For example, you could implement a voting feature by getting the total for the rating values for data uploaded in advance. When doing so, configure a minimum data rating value of 0 and a maximum data value of 1. If you then also set the option flag for the rating slot to RATING_FLAG_MODIFIABLE, you can set a restriction of one vote per user and limit users to a single vote per a set period of time when you configure the duplicate lock.

To use data stores as a counter across the entire game, someone has to upload the data. In this case, you can use the designated data ID upload feature so that it will upload only when data of the specified ID has not been uploaded. When using this feature, you begin with a rating. When there is no data, the workflow proceeds to the upload.

Negative values can also be specified and used freely as global variables for game participants, for example. However, relative comparison of these values is not supported, so you cannot filter data by values greater than or equal to a certain value.

Getting Random Data

To retrieve uploaded data at random, specify RESULTRANGE_ANY_OFFSET as the offset for the data to retrieve. This makes the server return pseudo-randomly selected data. Doing this makes it possible to prevent getting the same data every time.

Exchanging Data Among Individual Users

If you want to use data stores to exchange data among individual users, you can use data types to manage the received and unreceived data. For example, if you set 1 as the data type when you upload data that you want to use for data exchanges, other users can later set "data type 1" as a search condition to get data of that type. The user who has obtained this data can change the data type to 0 after they receive it to ensure that multiple users cannot get the same data. This step also allows the user that uploaded the data to later see which data was obtained.

You could also use tags to categorize the data for searches, but as mentioned in 4.2 Data Stores, NEX data stores are not designed to search for data over wide search ranges, so you should avoid this. The reason is because the server load increases as the number of sets of data increases, and this can lower the quality of service.
