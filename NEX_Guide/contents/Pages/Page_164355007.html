4.2 Data Stores

Data Search Conditions

You can use the tags specified during upload to search for data in the data stores. However, server performance might decline if you set tags that result in a disproportionate number of search hits. For example, if data is tagged with a country category such as "jp" and "us," all uploaded data will have one of these tags. If you then try to specify one of these tags to search for data in the data store, there will be a large number of matching records in the database, which may result in high server load and slow search performance.

For this reason, be sure to design a tagging scheme that does not concentrate on the use of only certain tags for searching. If you want to categorize data by country as in the preceding example, we recommend using data types.

Support for Handling Multiple Save Data Files

Data is managed based on the owner’s principal ID, which creates the possibility that your application may not be able to distinguish between multiple save data files. When the user uploads save data, the action might overwrite data uploaded earlier from a different save data file, so make sure to implement a means in your application to be able to identify the data itself.

We recommend checking with the user before deleting or overwriting data previously uploaded from a different save file. There is a risk of problems in the production environment if data is deleted or overwritten without user confirmation. However, this requirement does not apply to cases where game progress is not affected by the deletion of uploaded data.

For example, if only a limited number of data files can be saved and saving a new save data file requires deleting other data, we recommend displaying a message such as "You can only save up to XX data files. Delete data saved from another save data file, and save new data?" and get user confirmation before proceeding.

If a Nintendo Account is linked to multiple Switch consoles, the different consoles all access the data using the same principal ID. Be sure to implement your application so it can proceed without hindrance in such an event.

Storage and Availability of Data on the Server

Note the following points about the storage and availability of data that has been uploaded to the server using the Data Store feature.

  • Data storage is not completely assured.
  • Lost data cannot be recovered.
  • Sometimes data is temporarily inaccessible due to the state of the server.

Making the Scope of Data Update Permissions as Small as Possible

When using the data store feature to upload data to the server, we recommend making the scope of update permissions as small as possible.

By limiting the scope of these permissions, you can reduce the risk of data being illegally modified by malicious user activity. Use the following reference information to determine the most appropriate permissions.

When Only the Owner Updates Data

If only the user who uploaded the data themselves (the "owner") is allowed to perform updates, set DataStoreConstants::PERMISSION_PRIVATE. This permission is the default value for DataStorePostParam.

When Users Other Than the Owner Also Update Data
  • If the principal IDs of the users allowed to update data are known:
    Specify DataStoreConstants::PERMISSION_SPECIFIED. Afterward, specify the principal IDs.
  • If the principal IDs of the users allowed to update data are unknown:
    Specify DataStoreConstants::PERMISSION_PRIVATE. Afterward, the owner must use DataStoreClient::GetPasswordInfo() to get a password and share it with other users as needed. The password is a substitute for permissions.
When Using Uploads With a Specific Data ID

The data permission is set to DataStoreConstants::PERMISSION_PUBLIC. The scope of permission cannot be made any smaller.
