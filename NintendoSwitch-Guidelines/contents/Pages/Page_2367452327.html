E-commerce

This chapter covers requirements for application design and development that apply to applications using e-commerce features.
The guidelines in this chapter apply only to transactions that occur on Nintendo eShop using the Nintendo eShop balance. These guidelines do not apply to independent transactions on independent servers.

Info:

Nintendo is the seller of record for all transactions that occur on Nintendo eShop servers, even when the content is located on an independent server.

See below for definitions of terms used in this chapter. Refer to the Nintendo Switch E-Commerce Guide alongside this chapter.

Term Description

E-commerce items

A general term for the following content and services sold on Nintendo eShop

  • Downloadable content (DLC)
  • Consumable service items
  • Subscription service items
  • Bundle containing the above

For definitions of the different Nintendo platform server environments, see Nintendo platform server environments.

E-commerce: General

This subchapter covers requirements that apply to all applications that use e-commerce features.

0124: Prohibition of e-commerce items with content that deviates from your application's rating
The content of your e-commerce items must not deviate from your application's rating.
Software to Be Tested
Applications that use e-commerce items
Backgrounder

Switch does not support the display of ratings for each individual e-commerce item. Similarly, if a user purchases an e-commerce item with content that exceeds the rating of your application, the Switch system is not able to restrict use of the item based on its rating. Therefore it is prohibited for you to have e-commerce items whose content deviates from the rating of your application.
Test Method
Check the source code.
Pass/Fail Determination
Passes if no e-commerce items have content that deviates from the rating of the application.

0200: Disclosing probabilities for paid loot boxes (or paid gacha)
If your application allows users to get items from paid loot boxes (or paid gacha), then your application must display the probabilities of getting each item before the user makes the purchase, and these items must not be required to progress in the game.
Software to Be Tested
Applications that provide paid loot boxes (or paid gacha) through e-commerce
Backgrounder

In this guideline, "paid loot boxes (or paid gacha)" refers to paid in-game mechanisms that award randomized virtual items to players, for which the player pays either directly or with purchased in-game currency. (In-game mechanisms that award randomized virtual items to players for free are not considered to be paid loot boxes or paid gacha.) Applications that offer paid loot boxes must provide a method within the application for the player to view the correct probabilities of getting each item that it is possible to get from paid loot boxes.

The following are some ways of implementing these requirements:

  • Implement a button in the purchase flow labeled "Item drop rate" or similar, which displays the probabilities of getting each item when selected by the user
  • Display the probabilities of getting each item in a location that the user can check at any time, such as an in-game "Notifications" area
Info:

It is the responsibility of the publisher to ensure that the probabilities displayed within the application are correct.

You must display this information in a way that allows the player to understand the probabilities of getting each individual item. It is sufficient to display the probability on a category basis (such as by rarity or by item type) only if all items in each such category have equal drop rates. In addition, any items the user can get from paid loot boxes must not be required to progress in the game. Even if it is possible for the user to progress in the game without these items, it is also prohibited to design your application in a way that makes it extremely difficult for the user to progress without these items.
Test Method

You must perform both Test Method A and Test Method B below.

Test Method A

Progress to a point immediately prior to purchasing a loot box of your choice.

Test Method B

Check the source code.
Pass/Fail Determination

Passes if all of the following conditions are met.

  • For Test Method A, the application displays the probabilities of getting each item in a prominent location either before the user reaches the purchase screen, or on the purchase screen itself.
  • In Test Method B, if the application only displays the probability of getting categories of items, all items in a category must have the same probability.
  • In Test Method B, none of the items (or any future items) the user can get from paid loot boxes are required to progress in the game, and it is not extremely difficult for the user to progress without these items.

Service items

This subchapter covers requirements that apply to applications that use e-commerce features to support the sale of service items.

Info:

If your application provides consumable service items for sale in Japan, it is the responsibility of the publisher of your application to comply with the Act on the Settlement of Funds. In cases where the consumable service items supported by your application meet all of the following conditions, they may be considered equivalent to "prepayment" and therefore be subject to the Act on the Settlement of Funds.

  • sold in Japan
  • purchasable (not free)
  • expire more than 6 months after the date of issue

Note that even if the consumable service items are not referred to as currency, they may still be considered equivalent to "prepayment" depending on how they are used. For markets other than Japan, you must comply with local laws and regulations.

0146: Displaying the remaining time/uses of service items
Within your application, users must be able to check either the expiration date of their purchased service items, or the amount of time or uses remaining on their purchased service items.
Software to Be Tested
Applications that support the sale of service items
Exceptions
Service items that never have an expiry date or remaining number of uses to display
Backgrounder

You must display the expiration date or amount of uses remaining on any purchased consumable service items, and the amount of time remaining on any purchased subscription service items, in a location somewhere within the application that is easily visible to the user. However, service items that never have an expiry date or a remaining number of uses to display (such as the examples below) are not subject to this guideline.

  • Unlimited service items that can only be purchased once, but have no limit on remaining time/uses (such as access passes)
  • Instant service items whose licenses are used immediately upon purchase, so that the remaining uses are always "0"

Users can purchase service items for an application on Nintendo eShop even when that application is not currently running on the user's Nintendo Switch system. This means that after your application is started, it must check whether any service item licenses have been added before it displays the expiration date or number of uses remaining on consumable service items, and before it displays the amount of time remaining on subscription service items. If any licenses have been added, your application must update the information that it displays.
Test Method
  1. Play through all modes of the application from beginning to end, and check the amount of time/uses remaining on service items.
  2. Close the application.
  3. Add a service item license to the user account used in step 1. (If testing in the development environment, add a license by jumping to Nintendo eShop from within the application and purchasing the license. Then, on the ec applet's purchase completion screen, press the HOME Button and close the application.)
  4. Start the application, and select the user account that you added a license to in step 3.
  5. Go to a scene that displays the amount of time/uses remaining on service items.
Pass/Fail Determination

Passes if all of the following conditions are met.

  • In step 1, the application provides some mode where users can check the expiration dates or amount of time/uses remaining on purchased service items.
  • In step 5, the license added in step 3 has been added to the amount of time/uses remaining that you checked in step 1.

0132: Displaying errors for service items that are managed through independent servers
Your application must use the error viewer applet to display the following specific errors returned by the server API for service items.
Software to Be Tested
Applications that implement service item features via an independent server
Backgrounder

If something prevented a service item API function from completing successfully, it returns error information as its response. In general, error handling for these errors is left up to you when you implement your independent servers, but the following error codes must be displayed on the client side by your application. (Note that subscription service items and consumable service items have different error codes.)

  • For subscription service items:
    • 2621-1202(MandomError.SERVICE_MAINTENANCE)
    • 2621-9501(BaasError.SERVICE_MAINTENANCE)
  • For consumable service items:
    • 2622-1502(SugarError.SERVICE_MAINTENANCE)
    • 2622-9501(BaasError.SERVICE_MAINTENANCE)

When you display errors on the client side in your application, you must use the error viewer applet to display them.
Errors other than those above are generally resolved on the server side. But if your application's design requires you to display an eShop REST API error not listed above to the user, then display it with a message that suits your application's design. (For example, a general-purpose message such as "A communication error has occurred.")
References
  • Nintendo Switch E-Commerce Guide
  • Web tool to set errors for subscription service items
  • Web tool to set errors for consumable service items
Test Method
  1. Using the web tool to set errors (see References), set a SERVICE_MAINTENANCE error.
    (You must individually test each of the errors this guideline targets. To do this, first set one of the errors, then perform the following steps. Repeat until all errors have been tested.)
    • Subscription service items: 2621-1202, 2621-9501
    • Consumable service items: 2622-1502, 2622-9501
  2. Start the application.
  3. Play a mode in the application that uses subscription service items or consumable service items.
  4. In the web tool to set errors, clear the error you set in step 1.
  5. Proceed to a scene that calls the ec applet from within the application, and start Nintendo eShop.
  6. Purchase a service item.
  7. After completing the purchase on Nintendo eShop but before returning to the application, set the SERVICE_MAINTENANCE error again, the same as you did in step 1.
  8. Return to the application.
  9. Repeat steps 1 through 8 for all scenes that use subscription service items or consumable service items.
Pass/Fail Determination

Passes if the application uses the error viewer applet to display one of the following errors in steps 3 and 8, in accordance with the error you set in steps 1 and 7.

  • For subscription service items:
    • 2621-1202(MandomError.SERVICE_MAINTENANCE)
    • 2621-9501(BaasError.SERVICE_MAINTENANCE)
  • For consumable service items:
    • 2622-1502(SugarError.SERVICE_MAINTENANCE)
    • 2622-9501(BaasError.SERVICE_MAINTENANCE)

0164: Displaying errors for consumable service items that are managed through user save data
Your application must appropriately handle and notify the user of any errors that occur when using consumable service items that are managed through user save data.
Software to Be Tested
Applications that use consumable service items that are managed through user save data
Exceptions

When there is no disadvantage to the user even if the error is not displayed, such as in the following examples:

  • When the application automatically retries the operation and completes it without any problems
  • When the application can resolve the error without displaying it to the user
  • During (background) processes that do not involve active user interaction, where the error causes no problems that affect the user's ability to progress further in your application

  • When the nn::nifm::HandleNetworkRequestErrorResult() function is being used to notify users that they are not connected to the network
Backgrounder

If your application uses consumable service items that are managed through user save data, and the ec library returns an error that must be displayed, you must use the error viewer applet to notify the user of the error.

The following three categories of errors must be displayed.

  • If nn::account::ResultNetworkServiceAccountUnavailable is returned:
    • Handle as required by 0121: Implementing handling when your application is unable to use a network service account.
  • If nn::ec::ResultShowErrorCodeRequired is returned:
    • Use the GetErrorCode() function of the class that the error originated from to get the nn::err::ErrorCode structure, then pass it to nn::err::ShowError(nn::err::ErrorCode) to display the error.
  • If some error is returned other than a ResultShowErrorCodeRequired belonging to the nn::ec namespace:
    • Pass the returned Result to nn::err::ShowError(nn::Result) to display the error.
References
  • NintendoSDK Documents
    • Features > System > ec Library
  • Nintendo Switch E-Commerce Guide
Test Method
If nn::account::ResultNetworkServiceAccountUnavailable is returned:

Check the application's behavior by performing the Test Method in 0121: Implementing handling when your application is unable to use a network service account.
If nn::ec::ResultShowErrorCodeRequired is returned:

Configure the web tool to set errors (for consumable service items) to trigger error 2309-1502, and then play through all application modes that use consumable service items from beginning to end.
If some error is returned other than a ResultShowErrorCodeRequired belonging to the nn::ec namespace:

Check the source code.
Pass/Fail Determination
If nn::account::ResultNetworkServiceAccountUnavailable is returned:

Passes if the application passes the Pass/Fail Determination of 0121: Implementing handling when your application is unable to use a network service account.
If nn::ec::ResultShowErrorCodeRequired is returned:

Passes if the application uses the error viewer applet to display error 2309-1502.
If some error is returned other than a ResultShowErrorCodeRequired belonging to the nn::ec namespace:

Passes if the application uses the error viewer applet to display the error.

0161: Stating conditions when offering or extending passes for subscription service items for promotional purposes
If you offer or extend passes for subscription service items to users for promotional purposes, you must explicitly state the conditions and limitations for your promotion on Nintendo eShop, for example, in the description of the subscription service item.
Software to Be Tested
Applications for which you plan to use the Add Term License API to provide subscription service items via an independent server
Backgrounder

There may be instances where, as part of your day-to-day operations on Nintendo eShop, you use the Add Term License API to offer or extend passes for subscription service items for promotional purposes. When you do this, you must explicitly state your conditions and limitations for the offer on Nintendo eShop; for example, in the description of the subscription service item.
Some examples of such conditions and limitations include making the offer available only to users who access your service within a certain timeframe, offering only one pass per device, or extending the pass only an n number of times.

Info:

It is the responsibility of the publisher to handle all announcements and description of such promotions, either made in-game or through any other medium.

Nintendo expects that you will offer or extend passes only for promotional or compensation purposes. You must contact Nintendo if you wish to offer or extend passes for any other purpose. User compensation refers to situations where your application or independent server had some issue that caused a service outage, and you wish to compensate affected users.
References

  • Nintendo Switch E-Commerce Guide

Test Method
Check the source code.
Pass/Fail Determination
Passes if the conditions and limitations for offering or extending passes for promotional purposes are clearly stated on Nintendo eShop; for example, in the description of the subscription service item.

Displaying item lists within your application

This subchapter covers requirements that apply when displaying in-application lists of the items available for purchase on Nintendo eShop.

0171: Handling addition of elements to your item lists
Your application must operate correctly even when elements have been added to the item list that you get with the ec library.
Software to Be Tested
Applications that use the ec library to get item lists
Backgrounder

If your application uses the ec library to get item lists, then your application must parse the JSON data returned by the server to extract the item list data. Nintendo may add new elements and new data capacity for these elements to the JSON data without prior notice. To handle this, you must do the following.

  • Allocate and pass the necessary amount of memory to the ec library so that memory does not run out when the amount of data increases.
  • Do not parse the JSON data in such a way that parsing fails when an element has been added. For example, do not parse the JSON data by specifying an offset and attempting to always extract the item list from the same location.

You can use the JSON compatibility checking feature to check whether your application fulfills these requirements.

For more information about the JSON compatibility checking feature, see NintendoSDK Documents > Features > System > ec Library > Debugging > JSON Compatibility Check Feature.
References
  • Nintendo Switch E-Commerce Guide
  • NintendoSDK Documents
    • Features > System > ec Library > Debugging > JSON Compatibility Check Feature
    • Features > Controlling the Development Hardware > DevMenuCommand > Shop Features
    • Features > Controlling the Development Hardware > DevMenu > Shop Settings
Test Method

  1. On NCMS, register product information on dd1, and then distribute the information.

  2. Prepare a Nintendo Switch devkit initialized to NintendoSDK Firmware for NX 10.0.0-4.0 (NX Add-On 10.3.0) or later.

  3. Use the JSON compatibility checking feature to add dummy elements. You can add it using either of the following methods:
    1. Use DevMenuCommand to set "DevMenuCommand.nsp – shop set-json-dummy-element-of-ec-response --mode fixed".
    2. Start DevMenu, go to Shop, and set JSON Dummy Element Mode to Fixed.
  4. Check that the addition rate is set to the default setting (50%).
  5. Start the application, get the item list data, then play a scene that uses the data you got.
Pass/Fail Determination
Passes if the application can be played without problems.

Test Method

  1. On NCMS, register product information on dd1, and then distribute the information.

  2. See the table in the Backgrounder. From this table, select a country in a region where the application supports the sale of e-commerce items, and set a Nintendo Account to that country of residence.
  3. See the same table's Language column, and set that language to be used within the application.
    Note: If the application does not support that language, skip to step 6.
  4. Using the Nintendo Account from step 2, start the application.
  5. Proceed to a scene in the application where prices are displayed.
  6. Repeat steps 2 through 5 for all other countries in regions where the application supports the sale of e-commerce items.
Pass/Fail Determination

Passes if, in step 5, the inc_tax_message string in the table in the Backgrounder is displayed on the same screen as the price information. If there are multiple scenes that display prices, passes if this condition is satisfied in at least one scene.
