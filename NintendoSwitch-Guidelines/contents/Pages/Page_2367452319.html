Patches

This chapter covers requirements for application design and development that apply to applications that have patches.

Patches: General

0123: Limit on patch size

The size of a patch must be no larger than the following threshold value:

1.5 GiB
Software to Be Tested
Patches
Backgrounder

When you create patches, you must keep their size to no larger than the threshold value. If your patch absolutely must exceed this size limit due to your application's design, you must submit a request for an approval on Nintendo Developer Portal. This threshold value limit applies to the size of the NSP file for the patch you are submitting. For example, if you add 400 MiB of content in v1, then add another 400 MiB of content in v2 for an NSP file that is 800 MiB, this limit applies to the total 800 MiB size of the NSP file. (The limit applies to the cumulative total size of your latest patch. It does not apply to the relative increase in size between patches, which would be 400 MiB in the example above.)

Nintendo considers the reasons that your patch exceeds the size limit when deciding whether to grant waivers for this guideline. If you request a waiver, run AuthoringTool's analyze-patch command (shown below), and submit the results with your waiver request. Nintendo uses this as quantitative information about the patch size. The analyze-patch command is available in versions of AuthoringTool that support NintendoSDK NX Add-On 10.4.0 or later. Even if you are creating a patch in an older development environment, Nintendo recommends that you get a version of AuthoringTool that supports it and run analyze-patch.

AuthoringTool.exe analyze-patch patch-current.nsp [--previous patch-previous.nsp] --original application.nsp  --obfuscate-file-name

If your patch is v2 or later, you must always specify previous. For details about how to use this tool or for examples of its output, see the "Features > Patches > Optimization Information" section of the NintendoSDK Documents.

Along with the results of running analyze-patch, also provide the following information to explain the reasons why your patch exceeds the size limit and the reasons why you cannot reduce the size of your patch any further. As a basic rule, Nintendo may grant waivers for patches that exceed this limit as long as the patch size matches up to the amount of fixes and updates in the patch, so that the size feels reasonable to users.

  • List the content that is causing the patch to exceed the size limit, broken up by purpose and estimated size. (There is no need to list content that has little impact on the patch size.)
    Example: This patch adds map data taking up 300 MiB
  • If your patch exceeds the size limit because it includes content that is not actually being changed by the patch, explain the technical reason why your patch includes this content.
    Example: This application uses middleware that creates non-deterministic archives, taking up 500 MiB
  • Include the content and size of any patches you plan to release in the future, if you know such details
    Example: We expect future patches to reach up to 4.5 GiB in size

The "Patch size analysis" produced by analyze-patch provides a breakdown of your patch's size, which you can use for reference when checking why your patch size exceeds the limit. You can display actual filenames by leaving out the --obfuscate-file-name option. Feel free to provide the required information by taking the "Patch size analysis" output and simply adding your additional descriptions and explanations to it.

In the "Original size analysis" produced by analyze-patch, the field labeled "unused" indicates the size of the data that is no longer referenced after the patch is applied, either because those files were updated or because they were deleted. If this "unused" data exceeds 1 GiB, you must also explain why a high amount of data is no longer used, when explaining why your patch exceeds the size limit.

Below are some examples of ways patch sizes can increase and how to handle such situations. For details about the patch mechanism for Nintendo Switch and about ways to decrease patch size, see the "Features > Patches" section of the NintendoSDK Documents.

You want to distribute a patch that includes data just for users who have purchased downloadable content

Users who have not purchased your downloadable content will be forced to download the data as part of the patch even though they cannot use the data. Consider including this kind of data in your downloadable content instead. If you have both small and large files of this kind of data, it may also be effective to put the small files in your patch and put the large files in your downloadable content.

If there is a reason why you cannot include this data in your downloadable content, you must contact Nintendo to explain the reason. For example, you could write something like "Even for users who have not purchased the downloadable content, it is necessary for them to have this data so that they can see this data in network PvP matches" as your reason.

You want to update the middleware your application uses and reconvert the corresponding resources

There is no benefit for the user in receiving identical resources again in a patch, so including identical resources in your main application and in a patch is prohibited.

  • Investigate whether you can design your patch in such a way that it does not include the reconverted resources
    Adjusting the method that the middleware uses to reconvert the resources may allow you to prevent identical resources from being included in your patch again.
  • Check whether it is possible for you to continue using the previous version of the middleware without updating it
    When submitting a patch, you are allowed to use old SDK versions which Nintendo no longer accepts for submission.

On the other hand, the following are some cases where you must update your middleware and cannot avoid it. In these cases, contact Nintendo to explain the reason.

  • In order to use a feature provided in a new SDK version, you must update to the middleware version supported by that SDK
  • You must update the middleware to fix a fatal bug caused by the middleware
You want to convert existing resources to optimize performance

Performance optimization is not outright prohibited because it is also beneficial to users. But before you assume you must have a large patch, please investigate whether you can achieve both improved performance and small size.

  • Look into whether there is a way to convert the resources without increasing the size of the patch
    Adjusting the method that you use to convert resources may allow you to prevent your patch size from increasing.
  • If you have not yet submitted the initial version of your application, use your initial version to optimize any elements that may later affect patch size.

If it is difficult for your application to balance performance and size, contact Nintendo to explain the reason.

You want to put data you know you will revise later in a patch instead of the main application, to limit how much storage space each user needs

If your application is download-only and you know that some content of your initial application will be repeatedly modified by patches going forward, consider putting the actual data of the content you plan to modify in a patch instead of in your main application. Doing this can ultimately reduce the amount of combined storage space required for your application and its patches.
The purpose of this guideline is to limit the consumption of storage space, so Nintendo may approve your patch being large in such cases. Contact Nintendo with the size breakdowns for your main application and patch, as well as your planned patch release schedule.

If you are using NintendoSDK NX Add-On 13.x or later, you can use the ROM compression feature. This feature can help reduce the size of your application and patches if they contain compressible data. This feature compresses applications in a way that creates smaller patches. Using this feature for all your compression may ultimately make your patch size smaller than if you use a different compression scheme or use this feature on a pre-compressed application. Therefore, if you are using NintendoSDK NX Add-On 13.x or later, consider using this feature to compress the initial version of your application from the start, because that may also reduce your patch size. If you did not use the ROM compression features on the initial version of your application and then used the feature for the first time on a patch, the ROM compression feature may in fact increase the patch size. In such cases, you must make sure to test the feature and check that it actually does produce a smaller compressed file before you submit. For more information about ROM compression, see the NintendoSDK Documents > Features > Building > Creating Application Images > Resource Data (ROM) Compression.

Test Method

After loading the NSP file in AuthoringEditor, go to Basic > Size information and check the value displayed in the Patch install size field.
Pass/Fail Determination
Passes if the value displayed in AuthoringEditor under the Basic > Size information > Patch install size field after loading the NSP file is no larger than the threshold value.

0053: Prohibition of patches that make save data unusable

Users must be able to continue using their save data after they apply your patch.
Software to Be Tested
Patches
Exceptions
  • Applications that do not create save data
  • The following types of save data:
    • Option settings, temporarily suspended gameplay data, or other data that users can recreate relatively easily
    • Specific data that you deliberately break compatibility with as part of a specification change (for example, a patch that makes it impossible to watch previously-saved replay data)
Backgrounder

Your application must be backward-compatible with save data from earlier versions. This means that after applying the patch, users must still be able to use save data created by earlier unpatched versions of your application. For example, avoid any implementations where applying a patch would cause the application to assume that the previous save data is corrupted, making it impossible for users to progress, or causing the application to initialize the save data and erase their previous progress.
In contrast, save data created by your application after the patch does not need to work with earlier versions of your application before the patch. (In other words, your application does not need to be forward-compatible.)
It is not a problem to break compatibility with the following types of save data.

  • Option settings, temporarily suspended gameplay data, or other data that users can recreate relatively easily
  • Specific data that you deliberately break compatibility with as part of a specification change (for example, a patch that makes it impossible to watch previously-saved replay data)
Test Method
  1. Play the unpatched application and create an example of every kind of data.
  2. Apply the patch.
  3. Access and use all the kinds of data created in step 1.
  4. If you have already released previous patches, repeat steps 1 through 3 with all previously released versions, each time starting in step 1 with one more of the previous patches already applied.
Pass/Fail Determination
Passes if, in step 3, the previous save data is usable.
