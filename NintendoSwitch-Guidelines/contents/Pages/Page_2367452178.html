0120: Prohibition of displaying the support number or the network service account's internal ID
Your application must not display the support number or the network service account's internal ID to users.
Software to Be Tested
Applications that display an ID to identify the user
Backgrounder

Your application can get the internal ID of a network service account (the "NSA ID") with the nn::account::GetNetworkServiceAccountId() function, but the NSA ID is not intended to be user-facing.
Therefore, it is prohibited to display the network service account's internal ID in your application.

Likewise, the support number is intended to be used by customer support as a number that can only be confirmed on the Switch system menu by a specific user.
It is prohibited to display the support number in your application because if other users can see it, they might misuse it or use it by mistake.

If your application needs an ID that identifies users (such as for user support purposes), you must handle it in one of the following ways:

  • Use the support numbers that can be found on the Switch system menu
    • Instead of displaying the support number within your application, guide the user to find the support number on the "[User Name's] Page" section of the HOME Menu.
  • Prepare your own user identifier and display it in your application
Info:

If you guide the user to find their support number on the Switch system menu, see the Nintendo Switch Terminology for the terms to use when describing the system menu.
For example, using a message like the following in your application is acceptable.

  • "To check your support number, open the HOME Menu and go to your User Page."
References
  • Nintendo Switch Independent Server Setup Manual
    • Independent Server Operation
  • Nintendo Switch Terminology
Test Method
  1. Check the ID displayed in the application.
  2. Launch DevMenu, then under Accounts check the NSA ID linked to the user account that you used in step 1.
  3. On the HOME Menu, go to the "[User Name]'s Page" of the user account used in step 1, and check the support number.
Pass/Fail Determination

Passes if all of the following conditions are met.

  • The ID displayed in step 1 does not match the NSA ID checked in step 2.
  • The ID displayed in step 1 does not match the support number checked in step 3.

0121: Implementing handling when your application is unable to use a network service account
If an error is returned because your application is unable to use a network service account, you must call the specified function to display the recovery sequence.
Software to Be Tested

Applications that use network service accounts and call any of the following functions:

  • nn::account functions
  • nn::nex::NgsFacade::Login() function
  • nn::nex::SmartDeviceVoiceChatClient functions that trigger communication processing
  • nn::ens::SmartDeviceVoiceChatClient functions that trigger communication processing
  • nn::friends functions that trigger communication processing
  • Functions that return nn::ec or nn::account errors
  • NPLN functions that trigger communication processing
Exceptions

When there is no disadvantage to the user even if the error is not displayed, such as in the following examples:

  • During (background) processes that do not involve active user interaction, where the error causes no problems that affect the user's ability to progress further in your application
Backgrounder

In some situations, external circumstances may cause network service accounts to become unusable by your application. One such situation is when the Nintendo Account User Agreement (the EULA) has been updated and the user needs to agree to it again.

When this happens, you must make the network service account usable again by calling nn::account::EnsureNetworkServiceAccountAvailable() to make the system display the network service account activation sequence. You must then process the result returned by this function, as follows.

  • Function succeeded: Once more, run the function that previously returned the nn::account::ResultNetworkServiceAccountUnavailable error, and continue with the scene. (Proceed to the sequence that the application would have proceeded to if no error occurred.)
  • Function failed: Do not continue with the scene that requires a network service account.

When your application calls a function that requires a network service account and invokes the activation sequence, the activation sequence might fail. Even so, if you call such a function again and it still returns nn::account::ResultNetworkServiceAccountUnavailable, you must continue to display the activation sequence every time.
You must handle nn::account::ResultNetworkServiceAccountUnavailable errors in the way described above. You must not handle such errors using any other method (such as displaying the error via the error viewer applet).

Info:
  • If you called nn::nex::NgsFacade::Login(), and nn::nex::NgsFacade::GetLastLoginNnResult() returns nn::account::ResultNetworkServiceAccountUnavailable as its return value, it means that execution did not internally reach the point of signing in to the NEX game server.
    This means that if your application automatically calls nn::nex::NgsFacade::Login() again after nn::account::EnsureNetworkServiceAccountAvailable() succeeds, it is not a violation of "0024: Prohibition of unnecessary sign-ins to game servers".
  • The nn::nex::NgsFacade::Login() function is an overloaded function, meaning that it has multiple variations. The only variation that is subject to this guideline is the variation (provided up until NEX library version 4.4.0) that takes nn::account::UserHandle as an argument.
  • When the system runs the network service account activation sequence, it displays a screen that prompts the user to sign in to a Nintendo Account or an account for China. The network service account becomes available again once the user successfully signs in. This is also called "restoring availability" or "recovering availability".
  • For NPLN, an nn::account::ResultNetworkServiceAccountUnavailable error occurs in functions that trigger any communication.
    This means that if you have multiple NPLN functions that trigger communication, an nn::account::ResultNetworkServiceAccountUnavailable error may occur in the middle of any sequence that runs these functions immediately one after another.
    If this occurs, and it is difficult to retry from midway through the sequence, retry the entire sequence from the beginning.

0122: Prohibition of automatically retrying to get network service account ID tokens

If nn::account::ResultNetworkCommunicationError is returned when your application tries to get a network service account ID (an NSA ID token), you must not automatically retry to get it again.
Software to Be Tested
Applications that get NSA ID tokens
Backgrounder

The function that gets NSA ID tokens (nn::account::EnsureNetworkServiceAccountIdTokenCacheAsync()) accesses the authentication server if it is called when there is no cached NSA ID token present. The nn::account::ResultNetworkCommunicationError error cannot be resolved by system-side or application-side processing. When this error occurs, to avoid overburdening the authentication server, it is prohibited for your application to retry to get a network service account ID token automatically without user input. Note that if your application has successfully gotten an NSA ID token once and the operating system has a valid cache of the token, getting the token does not access the authentication server.

Info:

When Auth Debug Tool is configured to generate an error, different system versions will have different behavior when your application uses ShopServiceAccessor.

  • On system version 10.x series or later:
    • Use of ShopServiceAccessor is logged in Auth Debug Tool > Application Auth Logs.
    • When Auth Debug Tool is configured to generate an error, use of ShopServiceAccessor generates an error.
  • On a system version earlier than the 10.x series:
    • Use of ShopServiceAccessor is not logged in Auth Debug Tool > Application Auth Logs.
    • When Auth Debug Tool is configured to generate an error, use of ShopServiceAccessor does not generate an error.
References
  • NintendoSDK Documents
    • Features > System > Account Library
  • Nintendo Switch Network Error Simulation Manual
Test Method
  1. On Auth Debug Tool, configure the settings to create the "Application update is required" error on the Switch devkit you are using for the test.
  2. Hold down the POWER Button on the Switch devkit you targeted for an error in step 1, then on the Power Menu select to restart the devkit.
  3. Start the application and progress to a scene where the application connects to the network. If the error that you configured occurs, close the error viewer applet.
  4. Leave the application idle without user input for roughly five minutes.
  5. Open the Auth Debug Tool, go to Application Auth Logs, and check the NSA ID token acquisition logs for the Switch devkit you used.
Pass/Fail Determination

Passes if all of the following conditions are met.

  • The Auth Debug Tool > Application Auth Logs shows only one log of failing to acquire the NSA ID token ("Application update is required") from step 3.
  • The Auth Debug Tool > Application Auth Logs shows no logs of failing to acquire the NSA ID token ("Application update is required") for the period of time during which step 4 was performed.

Note that if your application has multiple services and each service gets one NSA ID token, then as long as these calls are not automatic retries in response to nn::account::ResultNetworkCommunicationError, it is acceptable to see up to one log per service.
Tips

If the NSA ID token cache is not valid, the following function calls may also trigger access to the authentication server.

  • Using ShopServiceAccessor
  • Calling NPLN communication functions

These features are not involved when getting NSA ID tokens, so they are outside the scope of this particular guideline.
If the NSA ID token cache is valid, these features do not access the authentication server and leave no logs. They also do not generate the errors described below.

However, if these features do access the authentication server, they are logged in Auth Debug Tool > Application Auth Logs. In that case these features also do generate errors after you perform Test Method steps 1 and 2.

  • Error generated by ShopServiceAccessor: 2181-4111
  • Error generated by NPLN communication functions: 2124-3001

If these features leave logs in the Auth Debug Tool when you perform the Test Method, check the source code to ensure that your application does not automatically retry these calls.

If your application is designed to call the function that gets NSA ID tokens only when ShopServiceAccessor or an NPLN communication function is successful, you cannot use this Test Method to confirm whether your application complies with this guideline. In that situation there is no way to test whether your application retries the function that gets NSA ID tokens, so you must check the source code to determine whether your application complies with this guideline.

0196: Providing an explicit and repeatable way for users to activate the network service account

Your application must provide an explicit and repeatable way for users to activate the network service account.
Software to Be Tested
Applications that call functions listed in the Software to Be Tested row of "0121: Implementing handling when your application is unable to use a network service account"
Exceptions

Applications that do not provide user-facing network services
("User-facing network services" refers to network services that are explicitly available to the user within your application. For example, rankings and matchmaking with other users are considered "user-facing network services." In contrast, communication for the purpose of collecting user play data is not considered a "user-facing network service.")
Backgrounder

Your application must provide an explicit and repeatable method that users can use to call the functions listed in the Software to Be Tested of "0121: Implementing handling when your application is unable to use a network service account."
Your application must also comply with "0121: Implementing handling when your application is unable to use a network service account" when handling function calls explicitly triggered by the user.

Nintendo requires you to provide a way for the user to deliberately activate the network service account, because inability to do so is a bad user experience and could cause problems related to Nintendo Switch platform operations.
Implementations like the following bad example violate this guideline.

  • The application has an online mode, but when it calls a targeted function in the background and finds that it is unable to use a network service account, it allows the user to play only in offline mode without providing any UI or other method to start online mode.

Calling a function in the background refers to function calls not triggered by active user interaction. For example, if you automatically call one of the targeted functions at application startup without an associated user operation to access a network feature, it falls under this definition.
It is not prohibited for your application to call a targeted function in the background, but it is prohibited for your application to do so without also providing some other way for the user to explicitly trigger these functions.

0134: Notifying the user when a network use request was refused

When a network use request was refused, your application must use the designated method to notify the user.
Software to Be Tested

Applications that use the NIFM library
Exceptions

When there is no disadvantage to the user even if the user is not notified, such as in the following examples:

  • When the application automatically retries the operation and completes it without any problems
  • When the application can resolve the error without displaying it to the user
  • During (background) processes that do not involve active user interaction, where the error causes no problems that affect the user's ability to progress further in your application
Backgrounder

If your application uses the nn::nifm::SubmitNetworkRequest() or nn::nifm::SubmitNetworkRequestAndWait() function to submit a network use request, and the request is refused (that is, if the nn::nifm::IsNetworkAvailable() function is not able to return true), then this state is likely to affect the user's ability to progress further in your application. In this case your application must immediately call the nn::nifm::HandleNetworkRequestErrorResult() function. Calling this function displays either the error viewer applet or the Internet Settings screen in response to the current situation; the applet or screen then notifies the user of the issue and provides a means of recovering from this state. For details of which situations users must be notified about, see the library API Reference pages and Manuals listed in the References below.

Note that if one of these errors occurs during a scene transition, it may be technically difficult for your application to notify the user immediately. If so, it is acceptable to wait until the scene transition finishes before notifying the user, because in this case the impact to the user from waiting is small.

Info:

If you use the nn::nifm::IsNetworkAvailable() function to check network availability and handle a false return value by calling the nn::nifm::HandleNetworkRequestErrorResult() function to notify the user of the error, you do not need to notify the user about any other errors returned from libraries that use networks.

0135: Handling Result values returned by account library

Your application must appropriately handle certain specific Result values returned by the account library.
Software to Be Tested

Applications that use the account library
Exceptions

When there is no disadvantage to the user even if the error is not displayed, such as in the following examples:

  • When the application automatically retries the operation and completes it without any problems
  • When the application can resolve the error without displaying it to the user
  • During (background) processes that do not involve active user interaction, where the error causes no problems that affect the user's ability to progress further in your application
  • Cases where the account library returns ResultNetworkCommunicationError, and then upon detecting that the network is unavailable, the application calls nn::nifm::HandleNetworkRequestErrorResult() to notify the user of the error.
Backgrounder
If the account library returns a Result value that your application must handle, it means that the library or environment is in a state that is likely to affect the user's ability to progress further in your application. Your application must always use the designated method to handle these Result values. See below for the Result values that your application must handle.
  • ResultNetworkServiceAccountUnavailable
  • ResultTokenCacheUnavailable
  • ResultNetworkCommunicationError

For details, see the library API Reference pages and Manuals listed in the References below.

Note that if these Result values occur during a scene transition or as the result of background processing not visible to the user, you may worry that suddenly displaying dialogs to the user would feel unnatural. In these cases, when you handle the Result, you can delay any parts of the handling that involve displaying things to the user.

Note that if you use nn::nifm::IsNetworkAvailable() to check network availability and handle a false return value by calling nn::nifm::HandleNetworkRequestErrorResult() to notify the user of the error, you do not need to notify the user about any other errors returned from libraries that use networks. (This applies when the Result returned from the account library is ResultNetworkCommunicationError.)

When a Switch application uses the nn::ldn::Initialize() function to initialize the LDN library and start local communication, it disconnects the Switch system from internet communication. When the Switch system reestablishes internet communication, it places a load on the Nintendo servers.
