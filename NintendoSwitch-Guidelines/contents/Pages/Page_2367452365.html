0192: Using the DirtyWord filter to check user-entered text

To prevent inappropriate words from being displayed, at specific times your application must use the DirtyWord filter to check text that the user has entered.
Software to Be Tested

Applications that meet all of the following conditions:

  • For sale in China
  • Includes features that display user-entered text
Backgrounder

Applications must not allow user-entered text to contain inappropriate words, and must not display inappropriate words. Your application must check user-entered text using the DirtyWord filter provided by the system, and must replace inappropriate words with alternate characters or otherwise take measures to prevent the display of such words.

The words registered in the DirtyWord filter are updated on an unpredictable schedule. The updates occur automatically, but these updates to the filter may add words that are also contained in text entered by the user in the past. Therefore, your application must check user-entered text not only when the user enters it, but also every time before displaying that text again. (For example, your application could use the time during scene transitions to check any user-entered text it is about to display.)

  • Text the user has entered
  • Text other users have entered
  • Text retrieved by the system
    • Mii nicknames, amiibo nicknames, and Switch user account nicknames
      Although users enter this text outside of your application, your application must check it.

0063: On-screen indication when writing to amiibo

Applications must do the following when writing to amiibo.

  • Display some sort of on-screen indication that writing is in progress and not to move the amiibo away.
  • Make it clear to the user whether the write succeeds or fails.
  • If the write fails, prompt the user to write to the amiibo again.
Software to Be Tested
Applications that write to amiibo
Backgrounder

When writing to an amiibo, you must display an explanation on-screen so that the user understands that writing is in progress and not to move the amiibo away. The on-screen indication is needed because failed writes and data corruption occur more easily with NFC technology than with system memory or USB storage.
In addition, your application must make it clear to the user whether the write to the amiibo succeeded or failed. When a write fails, prompt the user to write to the amiibo again.

The reason the application must clearly indicate success to the user when the write succeeds is to let them know it is now okay to move the amiibo away from the touchpoint. Otherwise, if the application requires some sort of other user operation to progress to the next sequence, the user has no way to tell how long they must hold the amiibo to the touchpoint. Consequently, if the application properly handles cases where the write fails and automatically proceeds to the next sequence when the write succeeds, then the user is already able to tell that the write succeeded and there is no need to explicitly indicate so.

Note that if the user touches a corrupted amiibo to the touchpoint, you must also let the user know its data is corrupted. For how to handle corrupted amiibo, see "0057: Handling corrupted amiibo touched to the touchpoint."
Test Method
  1. Successfully write game data to an amiibo.
  2. Write game data to an amiibo, but make the write fail by moving the amiibo away from the NFC touchpoint while it is being written to.
Pass/Fail Determination
Passes if all of the following conditions are met.
  • In step 1, the application displays some sort of on-screen indication that writing is in progress and not to move the amiibo away from the NFC touchpoint.
  • In step 1, the application notifies the user that the write succeeded.
  • In step 2, the application notifies the user that the write failed, and prompts the user to write to the amiibo again.

0055: Handling amiibo touched to the touchpoint
Your application must respond in some way to every amiibo the user touches to the touchpoint.
Software to Be Tested
Applications that use amiibo
Backgrounder

In scenes where the user touches amiibo to the touchpoint, your application must respond in some way to every amiibo that is touched to the touchpoint, no matter what type of amiibo it is. Even if your application does not support that amiibo—it has an unsupported NFP tag format version, or it has the character ID of a character you have no plans to support in your application—your application must still respond in some way when the user touches it to the touchpoint. If your application does not respond at all, the user has no way to tell whether this behavior is normal or whether the Switch system, the accessory hardware, or the amiibo itself is broken.

This requirement is tested using all three of the amiibo types below. The NTF files are included in the separately-released amiibo Data List package.

Table 1 amiibo to test
# amiibo type NTF file to use Description
1 amiibo supported by your application NTF file of an amiibo your application supports Checks whether your application responds to the amiibo that you informed Nintendo your application supports.
2 amiibo with a special character ID that will never be used for a retail product NVL-DUM1_00_00.ntf Checks whether your application responds to amiibo with a character ID your application has no plans to support.
3 amiibo with a special format version that will never be used for a retail product NVL-DUM4_00_00.ntf Checks whether your application responds to amiibo with an NFP tag format version your application does not support.
Info:

Types 2 and 3 in the table of Table 1 amiibo to test are the same for all applications, regardless of which amiibo each application supports. This means you do not need to prepare new tags for each of your applications when testing these categories of amiibo.

Info:

If the user takes an NFC tag that is not an amiibo and touches it to the touchpoint, that falls outside the scope of this guideline and is not subject to this requirement.
Test Method

Enter any scene where your application recognizes amiibo, and perform the following steps.

  1. Take an amiibo supported by your application and touch it to the NFC touchpoint.
  2. Take an amiibo with NVL-DUM1_00_00.ntf written to it, and touch it to the NFC touchpoint.
  3. Take an amiibo with NVL-DUM4_00_00.ntf written to it, and touch it to the NFC touchpoint.
Pass/Fail Determination
Passes if, in steps 1 through 3, your application responds in some way the user can notice.

0057: Handling corrupted amiibo touched to the touchpoint
When the user touches a corrupted amiibo to the touchpoint, your application must notify the user and attempt to either restore or reset the amiibo.
Software to Be Tested
Applications that use amiibo
Exceptions
Scenes that only use factory-hardcoded data and do not detect amiibo data corruption.
Backgrounder

The data in the data region of an amiibo may get corrupted if the amiibo is moved away from the touchpoint while it is being written to. When your application recognizes corrupted amiibo data, your application must notify the user that the amiibo they touched to the touchpoint has corrupted data.

Switch saves backup data that is used to restore amiibo, but in some cases—such as if the user is playing on a different system than the one they backed up the amiibo on—this backup data does not exist. When the system recognizes that the user touched a corrupted amiibo to the touchpoint, the system is also able to check whether backup data exists for that amiibo.

You must handle this situation in one of the following two ways depending on whether the backup data exists.

  • If backup data exists for that amiibo, your application must either open amiibo Settings in restore mode, or transition to your own independently implemented restore feature.
  • If no backup data exists for that amiibo, your application must notify the user that it may be possible to restore the amiibo on a system where they have used that amiibo before; and if they don't want to try restoring it, they can reset it from amiibo Settings in system settings.

Your application is not required to take these steps if it recognizes corrupted amiibo data in a scene that only uses factory-hardcoded data.

Info:

Factory-hardcoded data never changes from the values set at the factory, and cannot be corrupted by user operations such as moving the amiibo away from the touchpoint while it is being written to.
Test Method
  1. Write any data to the amiibo, either within the application, via amiibo Settings, or via some other method.
  2. Launch NfpDebugTool and select Break amiibo from the main menu.
  3. Take the amiibo from step 1 and touch it to the NFC touchpoint to corrupt the amiibo's data.
  4. In a scene of your application that supports interaction with amiibo, take the corrupted amiibo created in step 3, touch it to the NFC touchpoint, and restore the amiibo.
  5. Repeat steps 2 through 3 and once again corrupt the data on the amiibo restored in step 4.
  6. Next, go to the NfpDebugTool's main menu and select Backup data.
  7. Execute Initialize backup data to delete all backup data.
  8. In a scene of your application that supports interaction with amiibo, take the corrupted amiibo created in step 5 and touch it to the NFC touchpoint.
  9. Reset the corrupted amiibo created in step 5.
Pass/Fail Determination
Passes if all of the following conditions are met.
  • In step 4, your application notifies the user that the data on the amiibo is corrupted, and either transitions to the amiibo Settings in restore mode or to your own independently-implemented restore feature within your application. Also, after the transition to the restore sequence, the amiibo is restored with the data that you wrote to it in step 1.
  • In step 8, your application notifies the user that the data on the amiibo is corrupted, and also informs them that it may be possible to restore the amiibo on a system where they have used that amiibo before, and that it is possible to reset the amiibo from amiibo Settings in system settings instead of restoring it.

0059: Limits on automatic writes
If your application writes to an amiibo at automatic intervals, it must write no more than 4 times per minute.
Software to Be Tested

Applications that automatically write to amiibo.
Backgrounder

Excessively frequent writes to an amiibo NFP tag can shorten its usable life below the product lifetime expected by Nintendo.

If your application instructs the user to leave an amiibo in contact with the touchpoint and writes to the amiibo at repeated automatic intervals while it is in contact, do not write to the amiibo more than 4 times per minute.
Test Method
Applications using a NintendoSDK version in the 3.x series earlier than NX Add-On 3.6.0, or in the 4.x series earlier than NX Add-On 4.4.1:
  • Check the source code.
Applications using NintendoSDK NX Add-On 3.6.0 or later in the 3.x series, or NX Add-On 4.4.1 or later:
  1. Insert a microSD card into a Nintendo Switch devkit that has been initialized to NintendoSDK SystemUpdater for NX 11.0.0-6.0 or later.
  2. Start DevMenu, go to Debug > FS Access Log Mode, and set it to SdCard.
  3. Start the application (built with a build type of Release).
  4. For at least 10 minutes, play a scene that automatically writes to amiibo.
  5. Close the application.
    (The system saves access logs to the microSD card when the application is closed, the system transitions to sleep mode, or powers off.)
  6. Remove the microSD card from the devkit, and get the FsAccessLog.txt access log file located directly underneath the microSD card's root directory.
  7. Analyze the access log using the version of FsAccessLogChecker packaged with the NintendoSDK SystemUpdater that your devkit is currently initialized to.
Pass/Fail Determination
Applications using a NintendoSDK version in the 3.x series earlier than NX Add-On 3.6.0, or in the 4.x series earlier than NX Add-On 4.4.1:
  • Passes if the application does not automatically and periodically write to the amiibo more than 4 times per minute.
Applications using NintendoSDK NX Add-On 3.6.0 or later in the 3.x series, or NX Add-On 4.4.1 or later:
  • Passes if the result of the FsAccessLogChecker analysis is PASS.
Tips
Applications using NintendoSDK NX Add-On 3.6.0 or later in the 3.x series, or NX Add-On 4.4.1 or later:
  • You can combine the test for this guideline with the tests for "0011: Limits on frequency and amount of writing to storage media" and "0012: Limit on frequency of reading storage media."
  • Initialize your devkit using a NintendoSDK SystemUpdater package corresponding to any of the firmware versions listed on Nintendo Developer Portal > Developer Support > Nintendo Switch > Technical Information > Master Submission Information > Firmware Version Required for Testing.
  • Use the version of FsAccessLogChecker packaged with the NintendoSDK SystemUpdater that your devkit is currently initialized to.
