File system

This chapter covers requirements for application design and development and applies to applications that use the file system.

See below for definitions of terms used in this chapter.

Table 1 File System Terminology
Term Description
Storage media General term referring to game cards, system memory, microSD cards, and all other media accessible by the system.

Storage media

This subchapter covers requirements that apply to reading and writing data to storage media.

0011: Limits on frequency and amount of writing to storage media

Your application must comply with the following requirements when writing to storage media.

Your application must write to storage media no more than 32 times per minute on average, and must write no more than a total of 16 MiB per minute on average.
Software to Be Tested
Applications that write to storage media
Exceptions
  • If the application exceeds this frequency only when the user plays the application in an atypical way
  • If the application has already gotten approval from Nintendo in advance to temporarily exceed this frequency in scenes the user encounters infrequently
Backgrounder

Excessively frequent writes to writable storage media can wear out the storage media and shorten its usable life below the product lifetime expected by Nintendo.

In one average minute, you must limit write operations to storage media to no more than 32 times, and must write no more than 16 MiBs'-worth of files.

For example, if your application auto-saves roughly once every ten minutes, then in each auto-save you must call functions that perform write operations no more than 320 times total, and must write no more than 160 MiB of files total.

Applications that regularly save game progress need to be carefully designed. For example, in a visual novel or text-adventure game where you expect the average user to take about 1.5 seconds to read one line, do not save their progress every time you display a new line. Instead, do something like waiting until the user has read an entire page before saving.

For a list of functions that perform write operations, see NintendoSDK Documents > Features > Basic Features > fs Library > Debugging > Checking the Frequency of Access.

Info:

The overall fewer number of writes you perform, the more performance improves. Likewise, the fewer file system operations you perform, the fewer locations in your application are affected by storage media response speed. For more information about file system performance, see NintendoSDK Documents > Features > Basic Features > fs Library > Performance.

If your application's average frequency exceeds these frequency limits over 10 minutes of typical gameplay and it is difficult for you to comply with the requirements, you must contact Nintendo in advance and obtain approval. (You may disregard cases where your application exceeds the limits only when the user plays in an atypical way.)
When you contact Nintendo, provide the following information.
  • What situations cause your application to exceed the frequency limits, and how does your application exceed the limits?
  • What conditions trigger the write operations, and what kinds of write operations are they?
  • If the amount of writing changes depending on the user's progress in the game, how does the write size of each file change?
  • Access logs and gameplay video of the following gameplay:
    • At least 10 minutes of gameplay containing one or more scenes where the application exceeds these frequency limits
      • For example, if your application exceeds the frequency limits only on initial startup, start the game without any save data or CacheStorage when you play it.
    • At least 30 minutes of normal gameplay, starting from a point where the user has already made progress in the game
      • Restore save data from a point where the user has already made progress in the game, then play forward from that point. For applications that use CacheStorage, also restore the CacheStorage to a state corresponding to the user's progress in the game.
      • If the amount of writing changes depending on the user's progress in the game, play the game from a point where the write size of each file has gotten large.

Also note that you must provide your original access log, not simply the analysis result from FsAccessLogChecker. You can use Target Manager or Target Manager 2's remote video feature to record the gameplay videos.

Test Method

  1. Insert a microSD card into a Nintendo Switch devkit that has been initialized to NintendoSDK SystemUpdater for NX 11.0.0-6.0 or later.

  2. Start DevMenu, go to Debug > FS Access Log Mode, and set it to SdCard.
  3. Start the application (built with a build type of Release).
  4. Play through the application from beginning to end.
  5. Close the application.
    (The system saves access logs to the microSD card when the application is closed, the system transitions to sleep mode, or powers off.)

  • Spec
  • TotalTime
  • WriteSize
  • WriteAccessCount

If you are unable to avoid a FAIL result for one or more of these checks, contact Nintendo in advance to avoid delays. See the Backgrounder for more information.

    If your application rarely makes fs accesses, you must ensure that the 10 or more minutes of gameplay that you record for your access log includes operations involving fs accesses (such as saving or transitioning between scenes).

0012: Limit on frequency of reading storage media

Your application must not repeatedly read from the same location in storage media more than an average of once per second.
Software to Be Tested

All applications
Exceptions
  • If the application exceeds this frequency only when the user plays the application in an atypical way
  • If the application has already gotten approval from Nintendo in advance to temporarily exceed this frequency in scenes the user encounters infrequently
Backgrounder

There is an upper limit on the guaranteed number of times that read operations can be performed on storage media. Excessively frequent reads of the same region in storage media can wear out the storage media and shorten its usable life below the product lifetime expected by Nintendo.

To prevent this, do not repeatedly perform read operations from the same location in any storage media more than an average of once per second. For example: in an average ten-minute period, you must mount and unmount the same media no more than 600 times, and you must re-read the same region in the same file no more than 600 times.

If you need to repeatedly read data from storage media, find some workaround that does not exceed the frequency limit. For example, you could load a sizeable chunk of data into main memory, and then access that loaded data.
The following are examples of operations where you would need to be careful.

  • Application performs a read every time it displays a single character of a font.
  • Application performs periodic reads at an interval of every frame or second.
  • Application performs a read every time a character takes a step.

When you mount and unmount the same media, the same metadata is read as part of the mount and unmount operations, so this counts as repeatedly reading the same location in storage media. If the data read by one call overlaps with the data read by another call, this also counts as repeatedly reading the same region in the same file. If your application repeatedly reads the same file, but the region specified by offset and size does not overlap with previous reads, it does not count as repeatedly reading the same location. For a list of functions that perform read operations, see NintendoSDK Documents > Features > Basic Features > fs Library > Debugging > Checking the Frequency of Access.

Info:

This guideline is intended to help you avoid the "Read Disturb" phenomenon that affects NAND flash memory. "Read Disturb" is a phenomenon where data that is stored physically close to read locations can get corrupted.

Because the physical arrangement of data in NAND flash memory is different from the logical arrangement, it is not possible to know what data may get corrupted. If your application's resource data (its ROM) is corrupted, the user can recover it by redownloading it, but if their save data is corrupted they cannot recover it. If the system's firmware or metadata is corrupted, it may stop operating properly.

Info:

Nintendo provides a file data cache feature that allows you to automatically cache a file's data within the FS library. To use this feature, the application only needs to allocate memory for the file data cache, so it may be an easy way to decrease your read frequency. For more information, see NintendoSDK Documents > Features > Basic Features > fs Library > Manual > Features > File Data Cache.

This feature is available in NintendoSDK NX Add-On 5.4.0 and later.

Info:

If your application uses Unity, see Unity for Nintendo Switch Development Manual > Development Guide > Using AssetBundle.

Note that the file data cache function mentioned above is supported as of Unity for Nintendo Switch 5.1.0 2018/05/16, SDK 5.4.0, and Unity 2018.1.2f1. For more information, see "UI Reference > Player Settings > nn::fs Cache Buffer Size" in the Unity for Nintendo Switch Development Manual.

Info:

The overall fewer number of reads you perform, the more performance improves. Likewise, the fewer file system operations you perform, the fewer locations in your application are affected by storage media response speed. For more information about file system performance, see NintendoSDK Documents > Features > Basic Features > fs Library > Performance.

If your application's average frequency exceeds these frequency limits over 10 minutes of typical gameplay and it is difficult for you to comply with the requirements, you must contact Nintendo in advance and obtain approval. (You may disregard cases where your application exceeds the limits only when the user plays in an atypical way.)
When you contact Nintendo, provide the following information.

  • What situations cause your application to exceed the frequency limits, and how does your application exceed the limits?
  • Access logs and gameplay video of the following gameplay:
    • At least 10 minutes of gameplay containing one or more scenes where the application exceeds these frequency limits
    • At least 30 minutes of normal gameplay, starting from a point where the user has already made progress in the game
      • Restore save data from a point where the user has already made progress in the game, then play forward from that point. For applications that use CacheStorage, also restore the CacheStorage to a state corresponding to the user's progress in the game.

Also note that you must provide your original access log, not simply the analysis result from FsAccessLogChecker. You can use Target Manager or Target Manager 2's remote video feature to record the gameplay videos.

0013: Prohibition of implementations that depend on access speed

Your application must operate correctly even if there are changes to any storage media's access speeds.
Software to Be Tested
All applications
Backgrounder

Different types of storage media (system memory, game cards, and microSD cards) have different read/write access speeds. There are also individual differences within the same media type and across different sizes and models of the same media type, and access speeds to any single storage media may change over time as it wears out, the data on it becomes more fragmented, or for other reasons. This means that if you implement processing that depends on having a certain access speed when reading or writing to storage media, you may invite bugs caused when the actual access speed is different. To avoid this, avoid coding in a way that depends on having a certain access speed for any storage media.

For example, if you assume that loading should finish within 2 seconds at expected loading speeds, and then you hard-code that assumption into your program by forcibly stopping the read operation after 2 seconds and starting to render from the loaded data, you may cause lockups or other critical bugs when the read doesn't finish within the expected time. Avoid hard-coding assumptions about access speeds into your program.

To allow you to test for bugs that depend on access speeds, Nintendo has provided features to emulate three possible speeds of access to any storage media: Unvarying fast access speed (equivalent to accessing system memory), unvarying slow access speed (equivalent to accessing one of the slower microSD cards likely to be available on the market), and randomly-varying access speed. Use these speed emulation features to ensure that your application operates correctly at various access speeds and when speeds fluctuate.

Info:

Note that the speed emulation features do not guarantee the Nintendo Switch system's maximum and minimum access speeds to storage media in the future.
References
  • NintendoSDK Documents
    • Features > Basic Features > fs Library > Performance
    • Features > Basic Features > fs Library > Debugging > Checking Access Speed Dependency
Test Method
  1. Prepare a Switch devkit initialized to the most recent firmware version listed on Nintendo Developer Portal > Developer Support > Nintendo Switch > Technical Information > Master ROM Submission Information > Firmware Version Required for Testing.
  2. Remove the microSD card from the devkit.
  3. Install the application you are testing (main application, patches, and DLC) to the system memory of the devkit.
  4. In DevMenu, go to Debug > FS Speed Emulation Mode and set it to Faster, Slower, or Random, then start the application installed in step 3 and play through it from beginning to end. Do this for all three of the speed settings.
Info:

If there is insufficient free space in the devkit's system memory to install the main application, patches, and all downloadable content to system memory, use a UHS-I (Ultra High Speed Phase I) microSD card with a read speed of 60 to 95 MB/s.

Because the speed emulation features work by slowing down access to the storage media, it is best to perform this test using storage media that has a fast access speed to start with. When testing this guideline, always store the application you are testing in system memory, and do your best to store other associated data in system memory as well. On top of that, make sure to use the fastest microSD card you have access to.
Pass/Fail Determination

Passes if the application is playable without problems in step 4.

Save data

This subchapter covers requirements that apply when reading or writing save data.

0147: Using save data in a way that does not depend on what other accounts are linked
Your application must be able to inherit and continue using the same save data even when the linked accounts have changed.
Software to Be Tested
Applications that use save data
Exceptions
Data saved to network storage
Backgrounder

On Switch, it is possible for the user to unlink their user account from their Nintendo Account, or to change the Nintendo Account that is linked to a specific user account. If your save data depends on specific accounts being linked, a change in the linked accounts could make it unusable. It is therefore prohibited to design your application in such a way that a change in the linked accounts causes it to delete its save data or makes the save data unusable.

Note: In system versions 6.0.0 and later, users can no longer unlink their user account and Nintendo Account with a user operation. However, there is a possibility that customer support personnel could unlink accounts either now or in the future.
References
  • NPLN Manual
    • NPLN Programming Manual > Managing NPLN Users > UserConfig Settings and NPLN User Usage Patterns
      • Pattern 2: Use as Explicitly Created Users (Non-Prearranged Users) > Guideline Compliance When Using Non-Prearranged Users
Test Method
Note: In order to perform this test, the Switch devkit must be connected to the internet.
  1. Create a user account and link it to Nintendo Account A.
  2. With the user account linked to Nintendo Account A, play the application, perform a save operation, and close the application.
  3. In DevMenu, go to Accounts > (User account from step 1) > Unregister NSA and unlink Nintendo Account A from the user account.
  4. With the user account not linked to any Nintendo Account, load the save data you created in step 2 and make some progress in the application, then perform a save operation and close the application.
  5. Link the user account to a separate Nintendo Account, Nintendo Account B.
  6. With the user account linked to Nintendo Account B, load the save data you created in step 4 and make some progress in the application, then perform a save operation and close the application.
Info:

Applications that support NPLN and cache the NPLN user ID in save data
If your application falls into this category, then in the development environment, NPLN features are not available to you in step 6. This means that you cannot use the above Test Method to check this guideline. If your application saves the NPLN user ID in save data, check the details of your implementation to determine whether your application complies with this guideline.
Note that in the production environment, Nintendo compensates for changes in linked accounts so that your application can still use NPLN features when linked accounts have changed. For more information, see the NPLN Manual > NPLN Programming Manual > Managing NPLN Users > UserConfig Settings and NPLN User Usage Patterns > Pattern 2: Use as Explicitly Created Users (Non-Prearranged Users) > Guideline Compliance When Using Non-Prearranged Users.
Pass/Fail Determination
Passes if the application can continue using the save data in steps 4 and 6.
Tips

If the application requires the user account to be linked to a Nintendo Account in order to use save data, it is not a problem for testers to skip step 4.

0151: Using save data from migrated user accounts
Your application must be able to use its save data without problems even if the user account is migrated.
Software to Be Tested
Applications that create save data on the system
Backgrounder

A user account consists of a user identifier (nn::account::Uid), profile, and other information. Migrating a user account to another system moves the user account itself and all of its user save data to the other system. Moving to another system also causes the pseudo device ID (PseudoDeviceId) to change. This means that if you link your save data to the PseudoDeviceId, your application may no longer be able to use its save data properly after the user account is migrated.

You must ensure that your application does not link its save data to the PseudoDeviceId, and is able to use its save data without problems even if the user account is migrated.
References
  • NintendoSDK Documents
    • Features > Save Data > Features for Transferring and Copying User Save Data
      • User Account Migration
    • Features > Save Data > Notes When Using User Save Data
      • Pseudo Device ID (PseudoDeviceId)
Test Method
  1. Prepare a Switch devkit that can launch the DevMenu, has a user account already created on it, and has been initialized in DEV mode.
  2. Start the application, create save data for the user account, and close the application.
  3. Launch the DevMenu and display the Debug screen.
  4. Go to Reset Pseudo Device ID and select Reset.
  5. Start the application again and load the save data created in step 2.
Pass/Fail Determination
Passes if the save data can be properly used in step 5.
Tips

If you test your application using the method below (in which both the PseudoDeviceId and user identifier nn::account::Uid change) and your application passes, then your application successfully complies with both this guideline and "0152: Using copied user save data." If your application fails the test below, then it is possible that you are violating one or both guidelines. In that case you must test each guideline separately using its own individual Test Method in order to determine which guideline is being violated.

How to test 0151 and 0152 simultaneously:
  1. Prepare two devkits: Switch devkit A (with user account A already created on it), and Switch devkit B (with user account B already created on it). Also prepare one microSD card. Set up the devkits so that each can launch the DevMenu.
  2. Insert the microSD card in Switch devkit A and start up the system.
  3. On Switch devkit A, play the application and create save data.
  4. Start the DevMenu, go to SaveData, and select the save data for the account you used when creating save data.
  5. Press A to export the save data to the microSD card.
  6. Remove the microSD card from Switch devkit A and insert it in Switch devkit B.
  7. On Switch devkit B, start the DevMenu, go to the SaveData screen, and change the dropdown in the upper part of the screen from User to Backup in SD card.
  8. This displays the save data stored in the SD card. Select the save data you exported, press A, and on the next screen select Import.
  9. A list of accounts is displayed. Select the account you want to import to, then complete the import.
  10. On Switch devkit B, start the application and load the save data.
Pass/Fail Determination
Passes if the save data created on Switch devkit A in step 3 can be used without problems on Switch devkit B in step 10.

0152: Using copied user save data

Your application must be able to use its save data without problems even if the user save data is copied.
Software to Be Tested
Applications that create save data on the system
Backgrounder

Copying the user save data copies it to a user account with a different user identifier (nn::account::Uid). (There is no distinction between copying to another user account on the same Nintendo Switch system versus a user account on a different system.) This means that if you link your save data to the user identifier (nn::account::Uid), your application may no longer be able to use its save data properly after the user save data is copied.
You must ensure that your application does not link its save data to the user identifier (nn::account::Uid), and is able to use its save data without problems even if the user save data is copied. If your application's design requires it to link its save data to the user identifier (nn::account::Uid), contact Nintendo.

Use of Save Data Cloud backup, one of the services for Nintendo Switch Online members, counts as copying user save data between user accounts (and between devices).
