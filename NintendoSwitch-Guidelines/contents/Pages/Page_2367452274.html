Accounts

This chapter covers requirements related to accounts.

Accounts: General

This subchapter covers general requirements for accounts.

0153: Updating the user account state to reflect whether the user is playing your application
For the duration that a given user is playing your application, you must keep their user account in the Open (signed-in) state. Likewise, for the duration that a given user is not playing your application, you must keep their user account in the Close (signed-off) state.
Software to Be Tested
Applications that use user accounts
Backgrounder

In general, applications can associate individual periods of gameplay with specific users. (For example, if the user starts a play session by selecting save data to continue, you can assume the same specific user is playing during that entire session.) During these periods of gameplay, your application must set the user account of the currently-playing user to Open (signed-in) state. If multiple users are playing, you must set all participating users' user accounts to Open (signed-in) state. Likewise, when a specific user stops playing—for example, when they back out of that user account to a scene before user account selection—you must set their user account to Close (signed-off) state.

You must set the user accounts of users not playing your application to Close (signed-off), not Open (signed-in). But in applications where players take turns or alternate control of gameplay—for example, in a turn-based board game—you do not need to set non-active user accounts to Close (signed-off) while those users are waiting for their turns.

Info:
  • You must not set unqualified user accounts to Open (signed-in). For more information about unqualified user accounts, see "0176: Prohibition of setting unqualified user accounts to Open state."
  • The user must explicitly confirm which users are playing your application. For more information about selecting user accounts, see "0199: Prohibition of automatically identifying the users playing your application."
Test Method
Info:
  • Note that this test cannot be performed under Prod Mode (the mode a devkit operates under when it has been initialized by InitializeSdev or InitializeEdev to a firmware version that has the string "+ Prod" in its description).
  • Note that the devkit must boot to the DevMenu in order to perform this test.
  • Use firmware version NintendoSDK Firmware for NX 5.0.0-3 (NX Add-on 5.3.0) or later to perform this test.
  1. Register two or more user accounts on a Switch devkit.
  2. Start DevMenu, go to Debug > Initial Boot Menu and change this setting to DevMenu, then restart the Switch devkit.
  3. On DevMenu, go to Application and start the application you are testing, then proceed to the scene where you select a user account (or other information associated with a user account such as save data). Select the user account (or other information) you are using for this test.
  4. Play through all modes of your application from beginning to end.
  5. Transition to a scene in the application where the same user stops playing or is no longer playing the application. If no scene within the application fits this description, press the HOME Button and close the application.
Pass/Fail Determination
Passes if all of the following conditions are met.
  • At some point before the tester starts using the user account (or other information associated with a user account such as save data) in step 4, only the message User Opened "nickname of user account selected in step 3" is displayed in the upper left of the screen.
  • While the tester is playing the application in step 4, no unnecessary User Opened or User Closed messages are displayed in the upper left of the screen.
  • In step 5, only the message User Closed "nickname of user account selected in step 3" is displayed in the upper left of the screen.
Note:

Unnecessary User Opened and User Closed messages occur when an application changes a user account to the Open (signed-in) state while that user is not playing the application, or when an application changes a user account to the Closed (signed-off) state while that user is still playing the application.

0199: Prohibition of automatically identifying the users playing your application
Your application must not automatically identify the users who are playing, without associated user operations.
Software to Be Tested
Applications that identify the users who are playing and set those user accounts to the Open (signed-in) state
Backgrounder

Switch systems are expected to be shared between and used by multiple users. If your application automatically identifies the users who are playing without associated user operations, you might accidentally use the data of a user who is not actually playing. To avoid this, your application must use user operations to identify the user who is playing.

Info:
  • If your application is designed to have the user select an account from the HOME Menu before application startup, your application must set that selected user account to the Open (signed-in) state. In this case, there is no need to require a user operation inside the application to reconfirm which user started the game.
  • If the isSkipEnabled variable in nn::account::UserSelectionSettings is set to true, then the account management applet may skip its user selection step when Skip Selection Screen is enabled in system settings. It is not a problem if user selection is skipped in this situation. Note that the Skip Selection Screen option is not visible in system settings if more than one account is registered on the Nintendo Switch system.
Test Method
  1. Prepare a Switch devkit that has only one user account.
  2. Start DevMenu, go to Accounts > Firmware settings and deselect Skip user account selection if possible. Then go to Debug > Initial Boot Menu, change this setting to DevMenu, and restart the Switch devkit.
  3. In DevMenu, go to Application and start the application you are testing. Select the user account you left on the devkit in step 1, and play the application.
  4. Close the application. In DevMenu, select Accounts > + Add a user account and add a user account.
  5. In DevMenu, go to Application and start the application you are testing. Select the user account you created in step 4, and play the application.
Info:

If your application requires a linked Nintendo Account at startup (if "RequiredWithNetworkServiceAccountAvailable" is set for StartupUserAccount in the application's NMETA file), then the user account that you select in steps 3 and 5 must already have a Nintendo Account linked to it in advance.
Pass/Fail Determination
Passes if all of the following conditions are met.
  • In step 3, the application uses user operations to identify the user account that is playing, and only the message User Opened "nickname of user account left on the devkit in step 1" is displayed in the upper left of the screen.
  • In step 5, the application uses user operations to identify the user account that is playing, and only the message User Opened "nickname of user account created in step 4" is displayed in the upper left of the screen.

0168: Prohibition of requesting NSA ID tokens in applications that do not need to get NSA ID tokens
Applications that do not need to get NSA ID tokens must not request NSA ID tokens.
Software to Be Tested
Applications that do not need to get NSA ID tokens
Backgrounder

If you have not filled out requests to use NEX or independent servers on OMAS, then your application cannot get NSA ID tokens.

If such an application attempts to get an NSA ID token by calling nn::account::EnsureNetworkServiceAccountIdTokenCacheAsync(), it triggers an unnecessary access to the authentication server.

To avoid burdening the authentication server, applications that do not need to get NSA ID tokens are prohibited from calling nn::account::EnsureNetworkServiceAccountIdTokenCacheAsync().

You must take special care if you are taking code from an old application that used network features and reusing it in a new application that does not have network features. It is acceptable for your application to retain a function call to nn::account::EnsureNetworkServiceAccountIdTokenCacheAsync() in its source code as long as the logic of your program prevents this function from ever being called.
Test Method
Check the source code.
Pass/Fail Determination
Passes if the application does not call nn::account::EnsureNetworkServiceAccountIdTokenCacheAsync().

0169: Prohibition of using the sorting order of user accounts for any purpose other than displaying them in a list
Your application must not use the sorting order of user accounts (either their list order or the order in which they have been selected in the past) for any purpose other than displaying the list of user accounts within the application.
Software to Be Tested
Applications that use user accounts
Backgrounder

It is prohibited to use the sorting order of user accounts for any purpose other than displaying a list of user accounts within your application. It is prohibited to handle some user accounts differently from others based on their sorting order.
Sorting order includes the following orderings:

  • The list order of user accounts on the upper left of the HOME Menu
    • You can get this sorting order from most nn::account functions that return a list of user accounts, such as nn::account::ListAllUsers.
  • The selection order (the most recently selected user account)
    • You can get this from nn::account::GetLastOpenedUser(), the nn::account function that returns the last-selected user account.

The sorting order is defined to allow users to easily select the user accounts that they use most often.
It goes against this defined purpose of the sorting order to prioritize specific user accounts over others based on their order, or to deliberately handle some user accounts differently from others in order to give them different user experiences. Doing so is also prohibited because it can lead to problems like the following:

  • Users may mistakenly believe that this behavior with the user account configuration is standard for all applications.
  • If a user account that the user does not want to use is given special handling, it disregards the user's intentions.

The following are some examples of prohibited specifications:

  • Automatically selecting the first user account (the one displayed farthest left on the HOME Menu).
  • Automatically selecting the most recently selected user account.
  • Automatically using the first user account's information or save data.
  • Automatically giving the first user account a separate or special 'lead' role in an application with asymmetrical multiplayer (competitive play where some players have advantages or different status from the others), where the rest of the players have 'follower' or 'normal participant' roles.
Test Method
Check the source code.
Pass/Fail Determination
Passes if the application does not use the list order of user accounts for any purpose other than displaying the list of user accounts within the application.

0176: Prohibition of setting unqualified user accounts to Open state
Your application must not use nn::account::OpenUser() to set unqualified user accounts to the Open (signed-in) state.
Software to Be Tested

Applications that use NintendoSDK NX Add-on 6.x or later and also call nn::account::OpenUser()
Exceptions

Applications with UserAccountSwitchLock set to Enable in their NMETA file
Backgrounder

In firmware that supports NintendoSDK NX Add-On 6.x or later, the licenses for downloadable applications and downloadable content allow these types of content to be played on systems other than the "primary console" (formerly also called the "active console").

Only users who have a license for the application can play it on Switch systems other than the primary console. All other users on those systems are restricted (Unqualified) users and are prohibited from playing the application. If your application sets an unqualified user to the Open (signed-in) state using nn::account::OpenUser(), the system forces your application to close. Because of this, you must not set an unqualified user account to the Open (signed-in) state.

Firmware that supports NintendoSDK NX Add-On 13.2.0 and later supports relaxation of user account restrictions.

Relaxation of user account restrictions can promote user accounts that were Unqualified at application startup to Qualified while your application is running. If a previously-unqualified user account has been promoted to qualified status, and your application uses nn::account::OpenUser() to set this user account to the Open (signed-in) state, the system does not force your application to close. Therefore, it is not a problem to set promoted user accounts to the Open (signed-in) state.

The nn::account::ListAllUsers() function lists all users (including unqualified users), so you must be careful when using this function in your application. To list only qualified users, use nn::account::ListQualifiedUsers().

Likewise, you must be careful if your application sets nn::account::UserSelectionSettings::isUnqualifiedUserSelectable to true and then calls the account management applet, because the user may select an unqualified user account. In scenes where your application lets users select which user account to set to the Open (signed-in) state, you must either set isUnqualifiedUserSelectable to false before calling the account management applet, or—if the user selects an unqualified user account—wait until that user account is promoted to qualified before setting it to the Open (signed-in) state. If an unqualified user account is not promoted, you must not set it to the Open (signed-in) state.
In cases where your application lets the user select an unqualified user account, but then cannot set that user account to Open (signed-in) state because it is not promoted, you must not allow the user to play with that un-Opened user account. Allowing the user to play with an un-Opened account violates "0153: Updating the user account state to reflect whether the user is playing your application."

Info:

You can specify an NMETA file option to ensure that only user accounts that were selected before application startup can be set to the Open (signed-in) state. Applications that have this option enabled are not subject to this guideline.

This option is available in NintendoSDK NX Add-On 6.4.0 and later.
References
  • Nintendo Switch E-Commerce Guide
  • NintendoSDK Documents

    • Features > System > account Library > User Account

    • Features > System > aoc Library > Policy Setting for Changes to Available Content
Test Method
Info:

You must use a devkit running Firmware for NX 16.0.0-4.0 or later to perform this Test Method.

  1. Create at least two user accounts, and link at least one of them to a Nintendo Account.
  2. Start DevMenu, go to Debug > Initial Boot Menu and change this setting to DevMenu, then restart the system.
  3. In DevMenu, go to the Application tab and hover your cursor over the application you are testing.
  4. Press the + Button or − Button.
  5. Select or tap Unqualified User.
  6. Choose a user account to set to Qualified (one of the user accounts linked to a Nintendo Account in step 1) and set Force Unqualified For Debug to Disabled for that user account.
  7. Choose a user account to set to Unqualified (any user account other than the one set to Disabled in step 6) and set Force Unqualified For Debug to Enabled for that user account.
  8. Press the B Button or select Back to return to the application selection screen.
  9. In DevMenu, go to Application and select the application you selected in step 3. When asked which user account to use, select the user account that you set to Disabled in step 6. (This will make the selected account the only qualified user account.)
  10. Check all scenes that call nn::account::OpenUser(). (If the application asks you to select a user account, try selecting the user account you set to Enabled in step 7.)
Pass/Fail Determination

Passes if, in step 10, all scenes you check meet the following condition.

  • The system does not force your application to close.

0208: Prohibition of using Nintendo Account-related terms
You must not use Nintendo Account-related terms within your application.
Software to Be Tested

All applications

(Includes applications for China)
Exceptions

Any of the following

  • System features
  • Applications whose "Nintendo Account Linking (OAuth)" status on OMAS is set to "Approved"
Backgrounder

You must not use the following Nintendo Account-related terms within your application.

  • Nintendo Account
  • child account
  • sign in / sign out
    (when referring to authentication using a Nintendo Account)
  • create
    (when referring to creating a Nintendo Account)
  • link
    (when referring to associating a Nintendo Account with a user account)

The reason for this requirement is that the framework and terminology of Nintendo Accounts and related services may change in future. You must not use these terms within your application itself. Instead, use the applets provided by the system features as needed.

Info:

These terms are used within the Switch system features, but it is prohibited to use them within applications.
The following are some examples of implementations that violate this guideline, along with corresponding ways of complying with the guideline.

  • If your application displays Nintendo Accounts as an account service that players can use within the application:
Implementation that violates this guideline How to comply

Displaying a button labeled "Sign in with Nintendo Account"
(Selecting the button launches the account management applet)
  • Changing the button label to text that is more generic, such as "Play online"
  • Removing the button, and instead launching the account management applet automatically

In applications that offer multiple account services, displaying a button labeled "Nintendo Account" as one of the options that the player can choose


(Selecting the button launches the account management applet)
  • Changing the button label to simply "Nintendo"
  • Removing the button, and instead (if necessary) launching the account management applet automatically
  • When the user cancels out of the account management applet:
Implementation that violates this guideline How to comply
Displaying an independent error message that includes prohibited terms such as "You must link a Nintendo Account to play online."
  • Displaying no independent error message if the user cancels out of the account management applet (because the account management applet provides all necessary handling for Nintendo Accounts)
  • Changing the error message to text that is more generic, such as "This will disable online play."
References

    • Network Service Accounts, Nintendo Accounts, and Accounts for China > Nintendo Accounts

    • Network Service Accounts, Nintendo Accounts, and Accounts for China > Account Link Status

    • Network Service Accounts, Nintendo Accounts, and Accounts for China > Accounts for China
Test Method
Play through all modes of the application from beginning to end.
Pass/Fail Determination
Passes if the application does not use the prohibited Nintendo Account-related terms listed in the Backgrounder.

0209: Prohibition of using deprecated scope values to link external services with Nintendo Accounts
Your application must not get any deprecated scope of permissions (any deprecated values of scope) from Nintendo Accounts when linking Nintendo Accounts with external services.
Software to Be Tested

Applications that link external services with Nintendo Accounts

How to tell if your application is subject to this guideline

Your application is subject to this guideline if it displays an authorization page similar to the following when your application links Nintendo Accounts to external services.

Info:

Note that this guideline is referring to linking with Nintendo Accounts, not network service accounts. See the Nintendo Switch Account Guide for more information about the differences between these two types of accounts.
Exceptions
Applications that were approved to use the now-deprecated scope values before the end of 2021
Backgrounder

The following scope values are no longer available when linking external services with Nintendo Accounts.

  • user.birthday
  • user.email
  • user.basic
  • user.links.nintendoNetwork.id

New applications are prohibited from using these scope values.
If you have an existing application that was approved by Nintendo to use any of these scope values before the end of 2021, and if stopping use of these scope values would cause problems in your application, you are allowed to continue to use them under the Exception to this guideline.
Note that if you have a request to use any of these scope values that was approved by Nintendo before the end of 2021 (approved clients), and you add a new application to that request, the new application would technically be able to use the approved scope values. However, it is not allowed for your new application to use the now-deprecated scope values.
This guideline also applies to localized versions and sequels of existing applications. If you want to use any of these deprecated scope values in a localized version or a sequel, contact Nintendo.

    • Linking With Nintendo Accounts > Usage Requests
  • Nintendo Switch Account Guide

0156: Restrictions on frequency of calls to friends library API
When your application calls API functions that trigger server access, you must not call them more often than the limits set by the list in the Backgrounder.
Software to Be Tested
Applications that get profiles or that update presence status on the friend server using the friends library functions in the Backgrounder
Exceptions
Operations that users are relatively unlikely to perform
Backgrounder

It is prohibited to exceed the call frequency limits for the API functions listed below. Calling these functions excessively increases the load on the server, and could prevent the server from providing stable network services.
Call each of these functions no more often than the limit set for that function.

  • Updating friend presence:
    • Targeted functions
      • nn::friends::DeclareOpenOnlinePlaySession()
      • nn::friends::DeclareCloseOnlinePlaySession()
      • nn::friends::UserPresence::Commit()
    • Limits
      • Prohibited to call without a corresponding user operation
      • Calls that result from a corresponding user operation are allowed up to once per five minutes
  • Getting profiles:
    • Targeted functions
      • nn::friends::GetProfileList()
    • Limits
      • Prohibited to call without a corresponding user operation
      • Calls that result from a corresponding user operation are allowed up to ten times per minute

However, if users are relatively unlikely to perform the operations that call these functions, it is acceptable to have operations that call these functions in excess of these prescribed limits.
Examples of operations that users are relatively unlikely to perform:

  • Instead of pressing the A Button to proceed normally through a sequence, the user cancels out of the sequence and starts over.
  • The user repeatedly joins and leaves a specific mode.
  • The user repeatedly connects and disconnects from the network.
  • The user repeatedly closes and restarts the application.
Test Method

Updating friend presence:

  • Check the source code.
Getting profiles:
  • Check the source code.
Pass/Fail Determination
Updating friend presence:
  • Passes if calls to the targeted functions meet all of the following conditions.
    • The application does not call these functions without a corresponding user operation.
    • The application calls these functions no more often than once per five minutes as a result of a corresponding user operation.
Getting profiles:
  • Passes if calls to the targeted functions meet all of the following conditions.
    • The application does not call these functions without a corresponding user operation.
    • The application calls these functions no more often than ten times per minute as a result of a corresponding user operation.

0188: Prohibition of including UGC in friend invitation messages
Your application must not include UGC in invitation messages sent as part of the friend invitation feature.
Software to Be Tested
Applications that use the friend invitation feature
Backgrounder

Users who receive an invitation can check the text of the invitation message on their User Page.

Invitation messages are not designed for the purpose of exchanging UGC. Therefore, your application must use preset text for these messages, and must not include UGC.

As long as the message does not include UGC, it is acceptable to dynamically generate the message text from preset parts, such as mode name, number of participants, or other descriptors for the game session that the user is being invited to.

For definitions of UGC, see UGC: General. Likewise, see the Nintendo Switch Online Play Guide for details about the friend invitation feature.
References
  • Nintendo Switch UGC Guide
  • Nintendo Switch Online Play Guide
Test Method
  1. Prepare two Switch devkits, Switch devkit A and Switch devkit B.
  2. On devkit A, enter a mode that supports friend invitations, and then send an invitation to a network service account on devkit B.
  3. On devkit B, go to the User Page and check the content of the invitation sent in step 2.
Pass/Fail Determination
Passes if, in step 3, the invitation message on the User Page contains no UGC.
