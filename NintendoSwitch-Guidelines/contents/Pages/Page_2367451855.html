Your application must not display stereoscopic images using the features of 3D televisions.
Software to Be Tested
All applications
Backgrounder

Do not implement your application to display in 3D on 3D televisions. 0004: Avoiding screen burn-in when screen burn-in reduction is disabled

If your application disables the screen burn-in reduction feature, ensure that the output image has no parts that are continually displayed in the same location on the TV screen.
Software to Be Tested
  • Scenes that use the nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe function to disable screen burn-in reduction
  • Scenes that play video in the Offline Web Applet
  • Scenes that use the nn::oe::BeginMediaPlaybackSection function to disable screen burn-in reduction
Exceptions
Exceptions if using nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe():
  • The boundary line between the video-rendering area and margins outside of that area when playing non-predetermined video in an inset on the screen (shown in blue on Figure 1 Boundary line between video-rendering area and margins outside that area)
  • Scenes that use nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe() for 15 minutes or less
Exceptions if playing video in the Offline Web Applet:
  • Videos with a run time of 15 minutes or less
Exceptions if using nn::oe::BeginMediaPlaybackSection():
  • The boundary line between the video-rendering area and margins outside of that area when playing non-predetermined video in an inset on the screen (shown in blue on Figure 1 Boundary line between video-rendering area and margins outside that area)
  • Scenes that use nn::oe::BeginMediaPlaybackSection() for 15 minutes or less
Backgrounder

Switch has a screen burn-in reduction feature that lowers the brightness of the TV output after a certain length of time without user input. However, you can use the nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe() or nn::oe::BeginMediaPlaybackSection() function to disable screen burn-in reduction. Likewise, the screen burn-in reduction feature is automatically disabled while video is playing in the Offline Web Applet. This means that for the duration of video playback, you must avoid screen burn-in by ensuring that the output image has no static parts that are continually displayed in the same location on the TV screen.


One way of ensuring that the output image has no static parts is to change what every pixel on the TV is displaying over time. If the center area of the video shows a moving image but other parts (such as logos or text around the edges of the video) are static, those parts can burn into the screen over time. Instead, make sure that every pixel of the image changes over time.

If you use either the nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe() or nn::oe::BeginMediaPlaybackSection() function, you must re-enable the screen burn-in reduction feature whenever your application temporarily stops playing the video (such as when the user pauses it or when your application is displaying an error).


Note that if your application displays some non-predetermined video on the screen, you do not have to test for screen burn-in of the line on the boundary of the video-rendering area and the margins outside that area. This boundary line is shown in blue on the figure below.

Figure 1 Boundary line between video-rendering area and margins outside that area


Likewise, if you are using nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe() or nn::oe::BeginMediaPlaybackSection() for 15 minutes or less or if the video you are playing in the Offline Web Applet has a run time of 15 minutes or less, screen burn-in is unlikely, so you do not need to ensure that the output image has no static parts.

Info:

If you know that the duration of time without user input will last fifteen minutes or less, Nintendo strongly recommends that you use the nn::oe::SetUserInactivityDetectionTimeExtended function instead of the nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe function. For details on the differences between each function, see the References.

Note:

Nintendo plans to provide the nn::oe::SetUserInactivityDetectionTimeExtendedUnsafe() function starting in NintendoSDK NX Add-On 3.0.0.

Info:

The online web applet also has a video playback feature that disables screen burn-in reduction. Lotcheck does not test video played this way since the video is not part of your ROM, but if you use the online web applet to play video, you must still ensure that the output image has no static parts.

Capture feature

This subchapter covers how your application must handle the capture feature. The "capture feature" refers collectively to two features that use the Capture Button built into the Switch system: (1) a feature that captures still images of the application when the user presses the Capture Button, and (2) a feature that captures video footage of the application when the user holds down the Capture Button.

These captured still images and video footage are saved to system memory or the microSD card. From there they can be viewed in the album or posted to specific external social media or other sites.

Note that you can disable the capture feature throughout your entire application by configuring specific settings in your NMETA file. To disable the capture of still images, set the Screenshot element in your NMETA file to Deny. To disable the capture of video footage, you can either set the Screenshot element to Deny, or set the VideoCapture element to Disable. For details, see NintendoSDK Documents > Features > Building > Creating Application Images. This subchapter requires you to prohibit screen capture in specific scenes, but if your application disables the capture feature entirely, you do not have to implement the extra processing to prohibit screen capture in those scenes.

0008: Prohibition of capturing content whose rights are retained by a third party
Your application must not allow content whose rights are retained by a third party to be included in any still images or video captured by the user.
Software to Be Tested
Applications that contain content whose rights are retained by a third party
Exceptions

  • Applications for which the owner of rights to the content has given permission to include the content in still images and video captured by the user and posted to external social media

  • Applications in which screen capture is disabled

  • UGC
Backgrounder

Because some applications (such as video-on-demand services or e-book-type services) contain content whose rights are retained by a third party, allowing capture of these applications on Switch could lead to a scene of video or images of a page of a book being posted on external social media or other sites. In these applications, you must prohibit capture during scenes that contain such content to ensure that still images and video captured by the user do not include content whose rights are retained by a third party.

Displaying errors

This chapter covers requirements related to displaying errors using the error viewer applet.

For more information about errors that are not displayed in the error viewer applet, see the manuals for the various libraries and the applicable guidelines in other chapters of this document. Guidelines related to error display are tagged with the "Displaying errors" tag, so you can highlight this tag to see all the guidelines related to error display.

0111: Displaying application-specific errors that have error codes
Your application must use the error viewer applet to notify the user of application-specific errors that have error codes.
Software to Be Tested
Applications that display application-specific errors that have error codes
Backgrounder

Application-specific error codes may overlap with some other application's error codes and cause difficulties in customer support. To avoid this, use only the nn::err::ShowApplicationError function to create and display your own application-specific error codes.

When you use the nn::err::ShowApplicationError function, it displays an error code with the format below in the error viewer applet.

2-[ApplicationErrorCodeCategory]-[Any number you specify]

The ApplicationErrorCodeCategory is the error code category configured in the NMETA file that you use to create your application image, and is usually your application's initial code. If your application is part of a series and you want to use the same initial code as your ApplicationErrorCodeCategory throughout the series, go to Nintendo Developer Portal and enter that string in your Application Specifications forms under Application error codes used. For information on how to access these forms, see Additional information.

If you simply want to display an error message without an error code, it is not a problem to display that message independently on the application side without using the error viewer applet.

0079: Displaying errors using the error viewer applet
When specific libraries return errors, your application must use the error viewer applet to notify the user.
Software to Be Tested

Applications that use any of the following libraries: LDN, NEX, Pia, BCAT (BCAT data delivery), or NPLN
Exceptions

When there is no disadvantage to the user even if the error is not displayed, such as in the following examples:

  • When the application automatically retries the operation and completes it without any problems
  • When the application can resolve the error without displaying it to the user
  • During (background) processes that do not involve active user interaction, where the error causes no problems that affect the user's ability to progress further in your application

  • When the nn::nifm::HandleNetworkRequestErrorResult() function is being used to notify users that they are not connected to the network

  • When the application displays a message such as "You were disconnected from the network" after network disconnection
Backgrounder

If one of the following libraries returns an error that must be displayed, the error is likely to affect the user's ability to progress further in your application. Your application must use the error viewer applet to immediately notify the user of such errors.

  • LDN

    If using the nn::ldn::Connect function causes your application to receive an error because users are using different versions of local communication, you must use the error viewer applet to notify the user of this error.

    Info:

    If you find out that clients with older versions of local communication are not notifying the user of this error, then use an alternate method to warn the user that they may need to apply a patch to continue to use local communication in your application. Possible alternate methods include displaying a message on the host system or putting this information on your application's website.

  • NEX

  • Pia

  • BCAT
    • BCAT data delivery
  • NPLN

For information on which errors must be displayed, see the API Reference pages or Manuals for the individual libraries listed in the References below.
However, if one of these errors occurs during a scene transition, it may be technically difficult for your application to display it immediately. If so, it is acceptable to wait until the scene transition finishes before displaying the error, because in this case the impact to the user from waiting is small.

Note that if you use nn::nifm::IsNetworkAvailable() to check network availability and handle a false return value by either (1) displaying a message informing the user that they were disconnected from the network, or (2) by calling nn::nifm::HandleNetworkRequestErrorResult() to notify the user of the error, then you do not need to notify the user about any other errors returned from libraries that use networks.

Also note that if your application automatically retries any functions, you must comply with "0028: Prohibition of automatic retry" and not implement automatic retries in any situations where they are prohibited.

Info:

For displaying e-commerce-related errors, see the guidelines in the E-commerce chapter.

Auto-sleep feature

This subchapter covers how your application must handle the auto-sleep feature.

0130: Prohibition of using nn::oe::ReportUserIsActive function outside of the scenes or triggers you specified when you got Nintendo approval in advance
Your application must use the nn::oe::ReportUserIsActive function only for the scenes and/or triggers you specified when you got approval to use this function from Nintendo in advance.
Software to Be Tested
Applications that use the nn::oe::ReportUserIsActive function
Backgrounder

On Switch, the screen burn-in reduction feature activates after a set period of time has passed with no controller input. After that, the system automatically enters sleep mode. Calling the restricted function nn::oe::ReportUserIsActive resets the system's timer for time elapsed with no user input, and delays activation of the screen burn-in reduction feature.

Repeatedly calling the nn::oe::ReportUserIsActive function is equivalent to disabling the auto-sleep feature without the user's consent. To ensure that the auto-sleep feature behaves in the way that the user has configured it to behave, your application must not use nn::oe::ReportUserIsActive in any scenes outside of the scenes or triggers you specified when you got Nintendo approval in advance.

Info:

If you specified a trigger such as "the user pressing a button on a special accessory" when you got approval to use the nn::oe::ReportUserIsActive function from Nintendo in advance, your application must not call this function unless user input on the special accessory is actually occurring. In other words, every call must be actively triggered by user input. It is not acceptable to simply call nn::oe::ReportUserIsActive automatically in every frame of the scene.

Crash reports

This subchapter covers how your application must handle the use of crash reports. A "crash report" is a collection of stack traces and register values that describe an application's state when it crashed due to an unexpected error. If you have enabled crash reports for your application, then when your application crashes, the system generates a crash report and sends it to Nintendo's crash report server. As an application developer, you can use the crash report acquisition tool included in the NintendoSDK to get the crash reports that your users opted in to share with you. For details, see NintendoSDK Documents > Features > System > Crash Reports.


The system provides users the ability to opt in and opt out of sharing crash reports with you. As the application developers, you can only get the crash reports that users opted in to share with you.


Note that you can disable crash report generation for your entire application by configuring specific settings in your NMETA file. This subchapter requires you to disable crash reports in specific scenes, but if your application disables crash reports entirely, you do not have to implement the extra processing to disable crash reports in those scenes.


0154: Disabling crash reports during scenes where users input credit card information
Your application must disable the generation of crash reports in all scenes where your application instructs the user to input credit card information.
Software to Be Tested

Applications that meet all of the following conditions:

  • Applications using NintendoSDK NX Add-On 4.x or later.
  • Applications that have users input credit card information.
Exceptions
  • Applications in which the feature to generate crash reports is set to OFF in the NMETA file.
  • Applications that instruct users to input credit card information only within the ec applet or web applet.
Backgrounder

If your application crashes during a scene where the user inputs credit card information, the credit card information that the user filled in on the input form may be included in the crash report. To prevent this, you must use the nn::oe::DisableCrashReport function to disable crash reports in scenes where your application instructs the user to input credit card information.

All scenes within your application where the user can input credit card information are subject to this guideline, even if your application does not save the credit card information. This is because crash reports generated during these input scenes may include the credit card information.

Note, however, that information that users input in the ec applet or web applet is not included in crash reports. If your application instructs users to input credit card information only inside the ec applet or web applet, you are not subject to this guideline.

Info:

Credit card information refers to the credit card number, cardholder's name, expiration date, security code, and other such information written on a credit card.

Info:

If your application uses NintendoSDK NX Add-On 3.6.0 or later in the 3.x series, the nn::oe::DisableCrashReport function is not provided. For how to handle that case, see 0155: Prohibition of generating crash reports in applications where users input credit card information.

System ticks

This subchapter covers how your application must handle the use of system ticks. System ticks are a way of measuring time that is dependent on the system clock.

0166: Prohibitions when using system ticks in calculations
Do not convert the system time in ticks to a smaller or lower-precision type for use in comparison operations or similar calculations.
Software to Be Tested
Applications that use the nn::os::Tick class, POSIX, the nn::time library or any other form of system ticks
Backgrounder

It is not a problem to get a tick object with nn::os::GetSystemTick(), and then call tick.GetInt64Value() on it to get the raw value for the system time in ticks as an int64_t type. However, you must not convert this value to float, int32_t, or any other smaller or lower-precision type for use in performing equality or magnitude comparisons. The same applies to tick values you get using nn::time, C, POSIX, or C++.

Switch systems are not restarted frequently, and the system ticks continue counting while the system is in sleep mode, so system tick values may get extremely large.
If you convert the system time in ticks to a smaller or lower-precision type than int64_t, you may lose part of the data that represents the original system tick value. This causes comparison operations and similar calculations to give incorrect results. As a result, your application may become unable to start, or may experience extreme processing slowdown or other symptoms.

The following list contains some examples of classes and functions that may also use system ticks.

  • nn::time::StandardSteadyClock
  • nn::time::StandardUserSystemClock
  • nn::time::AdjustableUserSystemClock
  • nn::time::StandardNetworkSystemClock
  • nn::time::AdjustableNetworkSystemClock
  • clock_gettime
  • timespec_get
  • time
  • gettimeofday
  • std::chrono::system_clock
  • std::chrono::steady_clock
References


  • NintendoSDK Documents
    • Features > Basic Features > os Library > Manual > Features > Time Management > Using the Time Management Features
    • Features > Basic Features > os Library > Manual > Classes > Tick Class

  2. Restart the system.
  3. Start the application and play through all modes from beginning to end.
  4. Repeat steps 1 through 3 for all settings of Initial Tick Value other than Custom.
Pass/Fail Determination
Passes if the application starts and operates without problems in step 3.
Tips

For simplicity, this test procedure asks testers to test with all settings except Custom, but it is not a problem if you also test with Custom settings as necessary.

Whether these bugs occur depends on how your application is implemented. Test all preset settings for Initial Tick Value, starting with the smallest values and going up to the largest.

Alarms

This subchapter covers how your application must handle alarms. The alarm feature sends a notification to the user at a time and date specified by the application. For more information, see Nintendo Switch System Features Guide > Other Features > Alarms, or see the NintendoSDK AlarmNotificationKit Documents. (Note: This is part of the AlarmNotificationKit package, a private package you need to request permission to use.)

0193: Adding alarms
Your application must get user consent to add alarms, and must add them only in accordance with the user's wishes.
Software to Be Tested
Applications that use alarms
Backgrounder

It is prohibited to add alarms against the user's wishes or without the user's consent.
Your application must provide a UI for adding alarms that is in compliance with at least one of the following conditions.

  • The user adds each individual alarm separately by selecting its day of the week and its time
    • Because the user sets the time of the alarm in order to add it, there is no need to get additional user consent.
  • The application adds each individual alarm separately by suggesting its day of the week and its time, and gets user consent separately for each alarm
  • The application adds multiple alarms by suggesting multiple days of the week and/or multiple times, but gets user consent separately for each individual alarm
    • Take for example a UI sequence where the application suggests to the user "Would you like to set an alarm for 7:00 PM on every Monday and Tuesday?" and offers the options "Yes" and "No." These options for user consent violate this guideline because the user cannot give their consent separately for each day of the week.
      Instead, implement a UI sequence that allows the user to consent separately to each alarm. In the example above ("Would you like to set an alarm for 7:00 PM on every Monday and Tuesday?"), one way for the application to pass this guideline is to offer all four of the following options: "Add alarms for all suggested days," "Add alarm for Monday only," "Add alarm for Tuesday only," and "Do not add any alarms."
